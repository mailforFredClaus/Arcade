Part I — How Modern AI Works

1. The big picture: the AI stack in 2026

Modern AI is mostly one idea pushed very far: train a huge neural network to predict the next piece of data, then shape it into a useful assistant. Products differ mainly in how that model is wrapped, so learning the layers pays off immediately.

Read it bottom up: hardware runs inference software, which runs a model, which an orchestration layer turns into a product. When a tool disappoints you, the cause almost always sits in one identifiable layer.

Three ideas that explain most of what you will see

  1. Capability comes from scale. Quality improves predictably as parameters, training data and compute grow (the "scaling laws"). Training a frontier model costs hundreds of millions of dollars or more; running it costs a fraction of a cent to a few cents per chat turn. That asymmetry shapes the industry: a handful of labs train, everyone else rents.

  2. One model, many tasks. Classic machine learning meant one model per task: a classifier, a detector, a regressor. A foundation model is general, and you specialize it at use time with the context you give it, not by retraining. For an engineer this is the big shift: most of the "programming" of an AI system is writing context.

  3. The weights are frozen; the system around them is not. Using a model never changes it. Everything it knows about your problem arrives through its context window on each request. When an assistant "remembers" you, software is re-inserting saved notes into that window.

Most bad comparisons mix layers. A model is the trained network you call; a product is the app built around it; a harness is the agent software that drives the model through tools.

2. How a large language model works

An LLM is a function that maps a sequence of tokens to a probability for every possible next token. Generating text means calling that function in a loop. Chat, reasoning and tool use are all built on this one loop.

The model's general knowledge lives in the transformer's weights; everything it knows about your task lives in the token sequence.

Tokens: the unit of everything

Text is chopped into tokens: common words are one token, rare words several fragments. In English, 1,000 tokens is roughly 750 words; code, numbers and non-English text take more. Price, context limits and speed are all counted in tokens.

Token counts are not comparable across vendors, or even across generations. Anthropic notes that Claude models from 4.7 onward use a tokenizer that produces about 30% more tokens for the same text (pricing). As a rough guide, a 10,000-line C++ project is on the order of 100,000 tokens.

Tokenization also explains some odd failures. A number like 3.14159 may split into several pieces, which is one reason models do arithmetic badly in their heads and well when they write code to do it.

Embeddings and the transformer

Each token ID is looked up in a table and becomes a vector of a few thousand numbers. Position information is mixed in, so the model knows word order. The vectors then pass through a stack of identical layers, from dozens to over a hundred. Each layer has two parts:

  • Attention. Each token scores how relevant every earlier token is and pulls in a weighted mix of their information. This is how "it" gets linked to the right noun 3,000 tokens back.

  • Feed-forward (MLP) block. Each token's vector is transformed on its own. Much of the model's stored knowledge is thought to live in these weights.

Each layer adds its result to a running vector per token, called the residual stream. A loose analogy: the residual stream is a state vector, each layer is an update step, and attention is a learned, data-dependent coupling between tokens. Loose, because nothing is conserved and every "step" has its own weights.

Two architecture variants matter in 2026:

  • Mixture of experts (MoE). The MLP is split into many experts, and a router activates a few per token. DeepSeek V4-Pro has 1.6 trillion parameters but uses only 49 billion per token (NYU RITS). You get big-model knowledge at small-model compute, but every weight still has to sit in memory.

  • Hybrid layers. Some open models replace part of the attention with linear-time layers (Mamba-2, DeltaNet) to make long context cheaper. Qwen3.8 and NVIDIA's Nemotron 3.5 both do this (Qwen3.8-27B, Nemotron 3.5 Bolt).

Sampling: where the randomness comes from

The last layer outputs a score (logit) for every token in the vocabulary, and a softmax turns the scores into probabilities. A sampler then picks one token:

Local engines expose every knob, and model cards list the recommended values.

Prefill and decode: why speed has two numbers

  • Prefill reads your whole prompt in parallel. It is compute-bound and fast, thousands of tokens per second, and it sets the wait before the first token.

  • Decode produces one token at a time, and each step must stream every active weight from memory. It is bound by memory bandwidth: tens to a few hundred tokens per second on a local GPU.

That split drives the hardware rules in Chapter 8: memory capacity decides what fits, memory bandwidth decides how fast it talks.

What an LLM is not

  • Not a database. It reconstructs plausible text from compressed statistics; nothing is looked up. That is why it can be fluent and wrong in the same sentence.

  • Not learning from you. The weights do not change while you use it.

  • Not a mere autocomplete. Post-training (next chapter) turns the predictor into a system that plans, uses tools and checks its own work, measurably well.

3. How models are made

A modern model is built in two stages: pretraining makes it knowledgeable, post-training makes it useful. Most of the 2025–2026 gains in coding and agents came from the second stage, especially reinforcement learning on tasks whose answers can be checked automatically.

The pipeline

  1. Data. Trillions of tokens of web text, books, code and papers, plus a growing share of synthetic data written by earlier models. Filtering and deduplication matter as much as volume.

  2. Pretraining. The model learns to predict the next token across all of it, on thousands of accelerators for months. The result is a base model: knowledgeable, but it continues text rather than following instructions.

  3. Supervised fine-tuning. Training on curated example conversations teaches the format: answer the question, follow instructions, call tools correctly.

  4. Preference training. The model is tuned toward responses that people (RLHF) or AI judges guided by written principles (RLAIF, including Anthropic's Constitutional AI) rate as better. This shapes helpfulness, honesty and tone.

  5. Reinforcement learning with verifiable rewards. The model attempts problems with checkable outcomes, such as math with known answers, code against tests and multi-step tasks in sandboxes, and is rewarded for success. Long chains of reasoning and dependable tool use come from here.

  6. Safety testing and release. Red-teaming, capability evaluations and runtime safeguards, documented in a system card.

The practical consequence: models are strongest where training could check their work (code that runs, math with answers) and weakest where it could not (niche facts, judgment calls, your company's conventions).

Reasoning models and test-time compute

Since OpenAI's o1 in September 2024, frontier models can think before answering: they generate a hidden chain of reasoning tokens, then the reply. More thinking buys accuracy on hard problems at the cost of latency and money. That makes inference-time compute a second scaling axis, next to model size.

Mixture of experts in practice

Most large open models are now MoE: Kimi K3 has 2.8 trillion parameters with 104 billion active per token, and Qwen3.8-Max has 2.4 trillion with 95 billion active (NYU RITS, DataNorth). The rule to remember: compute per token scales with active parameters, memory with total parameters. A 35B model with 3B active runs about as fast as a 3B dense model, provided all 35B fit in memory. That property drives several hardware choices in Chapter 8.

Distillation: why small models got good

Large models teach small ones: training a compact model on a frontier model's outputs transfers much of the skill. That is why the cheap tiers (Claude Haiku 5.5, Gemini 3.8 Flash, GPT-6 Luna) are capable, and why open models that fit on one consumer GPU now beat the frontier models of two years ago on many benchmarks.

Knowledge cutoffs and release cadence

Training data stops at a cutoff date: June 2026 for the current Claude 5.5 models (models overview). Anything newer reaches the model only through search, tools or what you paste in. Before trusting an answer, ask whether the fact could have changed since the cutoff; library versions and APIs are the usual trap.

The frontier moves every few months. Between September 1 and October 7, 2026, Anthropic shipped Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, OpenAI shipped the GPT-6 family, and Google announced Gemini 4 Argon. Build workflows that survive a model swap: keep prompts, evals and tool integrations portable, which open standards like MCP and Agent Skills make easier.

Safeguards and refusals

Labs train behavior policies and add runtime safeguards on top. Claude Fable 5.1, for example, routes some cybersecurity and biology requests to other models, while Claude Mythos 5.1, built on the same model with looser safeguards, is limited to verified organizations (Fable, Mythos). When a legitimate engineering request gets an odd refusal, adding the context that makes its purpose clear usually resolves it. System cards document what each model was tested for and are worth skimming for any model you depend on.

4. Context windows, memory, and retrieval

The context window is the model's entire working memory for one request: system prompt, tool definitions, conversation, files, tool results and its own output. Current Claude models take 1 million tokens of context and up to 128,000 tokens of output (models overview). How well you fill the window matters far more than how big it is.

What fills the window

  • Fixed overhead. The harness's system prompt plus every tool definition. Each connected MCP server adds its tool descriptions, so an agent can spend tens of thousands of tokens before you type a word.

  • Standing instructions. Files such as CLAUDE.md, loaded at the start of every session.

  • The conversation. Every turn, re-sent on every request.

  • Files and tool results. Usually the bulk: source files, logs, search results, command output.

  • Thinking and output. The model's own reasoning and reply also occupy the window.

For scale: 1 million tokens is roughly 750,000 words, about 1,500 pages of prose, or a mid-size codebase. Other flagships are similar: the GPT-6 family accepts 1.05 million tokens, Gemini 4 Argon 1 million, Grok 4.7 500,000 (The Batch, Google, xAI). Local open models typically support 128,000 to 262,000 tokens, though your VRAM usually caps you lower.

Bigger is not the same as better

Finding one fact in a long context is close to solved. Combining many scattered facts across hundreds of thousands of tokens is not, and instruction-following degrades as the window fills, an effect often called context rot. Long context is a capability, not a strategy.

  1. Curate. Give the model the relevant 20,000 tokens, not everything you have.

  2. Order. Put long documents first and your question and instructions last, as Anthropic's long-context guidance recommends (long-context tips).

  3. Label. Wrap each document in tags with its source, and ask the model to quote the relevant passages before answering.

  4. Reset. Start a fresh session for a new task instead of dragging stale context along.

The KV cache: why long context costs memory

To avoid recomputing attention over the whole history at every step, the model stores a key and a value vector per token, per layer. That store, the KV cache, grows linearly with context length:

\text{KV bytes} = 2 \times n_{\text{layers}} \times n_{\text{kv heads}} \times d_{\text{head}} \times \text{bytes per value} \times n_{\text{tokens}}

A 32B dense model of the Qwen3 kind (64 layers, 8 KV heads of 128 dimensions) at 16-bit precision needs 256 KB per token: 8 GB at 32,000 tokens and 32 GB at 128,000. At long context the cache can outgrow the weights. Hybrid models with linear-time layers shrink it, and 8-bit cache quantization halves it at small cost (Chapter 18).

On hosted APIs the same physics shows up as price. Claude Haiku 5.5, for example, charges five times its base rate for prompts over 100,000 tokens (pricing).

Compaction, context editing and memory files

  • Compaction summarizes older history to free space. Claude Code compacts automatically and on /compact; the API offers server-side compaction in beta (compaction).

  • Context editing clears stale tool results and thinking blocks automatically, also in beta (context editing).

  • Memory across sessions is always text that gets re-read: CLAUDE.md and auto memory in Claude Code, memory in the Claude app, the memory tool in the API. Keep it curated; Anthropic suggests keeping each CLAUDE.md under about 200 lines (memory).

Prompt caching: the cheapest optimization there is

The provider keeps the processed state of a prompt prefix, and any later request that starts with exactly the same prefix skips that work. On Claude, a cache write costs 1.25× the input price for a 5-minute cache or 2× for 1 hour, and a cache read costs 0.1×, or 0.05× on Opus 5.5 and Sonnet 5.5 (prompt caching). Re-sending a 200,000-token project context to Opus 5.5 costs $0.80 uncached and $0.04 from cache.

The rule: stable content first (system prompt, tools, reference documents), variable content last, because any change early in the prompt invalidates everything after it. Claude Code and the Claude app cache for you; in the API you mark up to four cache breakpoints, with a 512-token minimum on current models. Local engines reuse prompt prefixes the same way.

Retrieval: embeddings and RAG

An embedding model maps text to a vector so that similar meanings land close together; that powers semantic search, clustering, deduplication and classification. Retrieval-augmented generation (RAG) chunks your documents, embeds them, retrieves the best matches for each question and inserts them into the context with source labels, so the model can answer with citations.

SituationBest approach

For technical text full of exact identifiers (requirement IDs, part numbers, function names), hybrid retrieval that combines keyword search with vectors, followed by a reranker, beats pure vector search. Chapter 20 builds a local RAG pipeline.

5. Beyond text: vision, images, video, audio, and world models

The transformer machinery from Chapter 2 now reads images, audio and video, and a second family, diffusion and flow models, generates them. For a simulation engineer the generative side is unusually easy to understand: an image sampler is an ODE integrator.

Vision: models that read images

Images are cut into patches, and each patch becomes a token-like vector processed alongside the text. Claude, GPT and Gemini all read screenshots, photos, plots, scanned documents and diagrams. Claude accepts PDFs of up to 32 MB and 600 pages per request on its 1M-context models (PDF support).

  • Strong at: reading plots and dashboards, transcribing whiteboards, extracting tables from scans, critiquing a figure, describing a UI.

  • Weak at: exact measurements from pixels, counting many small objects, fine spatial relationships in dense engineering drawings.

When precision matters, give the model the underlying data instead of a picture of it.

Image generation: diffusion and flow matching

Training takes real images, adds noise at random strengths, and teaches a network to undo it: either to predict the noise (diffusion) or the velocity that carries noise toward the image (flow matching). Generation starts from pure noise in a compressed latent space and integrates step by step toward an image, steered by your prompt.

The analogy here is exact, not loose. A flow-matching model defines an ODE, and samplers such as Euler, Heun and DPM++ are numerical integrators. "Steps" are time steps, the "scheduler" is the step-size schedule, and distilled "turbo" models are trained to take 4 to 8 large steps instead of 20 to 50.

Video

Video models denoise a whole clip at once in a space-time latent, so compute grows with frames times resolution. That is why open models produce clips of roughly 5 to 20 seconds, and why a 5-second 720p clip takes minutes even on a high-end consumer GPU (Comfy docs, dev.to). The 2026 advance is joint audio and video: LTX-2.5 generates synchronized sound with clips of up to 20 seconds (LTX-2.5). Chapter 19 covers running these.

Audio

Speech-to-text models of the Whisper kind run locally in near real time on modest GPUs. Text-to-speech and speech-native assistants (voice modes in Claude, ChatGPT and Gemini) round out the set. The underrated use: dictating prompts. Good prompts are long, and speaking is far faster than typing.

World models and AI for physical systems

  • World models learn how an environment evolves under actions. NVIDIA's open Cosmos 3 (June 2026) predicts future world states and serves as a backbone for robot control policies (NVIDIA). Google DeepMind's Genie 3 generates interactive worlds you can walk through (Project Genie).

  • AI-native simulators. Isaac Sim 6.0 (Apache-2.0, generally available June 2026) ships an MCP server and a Claude Code skill, so an agent can drive the simulator directly (NVIDIA forum).

  • Neural surrogates replace or accelerate expensive solvers. NVIDIA PhysicsNeMo packages physics-informed networks, Fourier neural operators and graph networks for CFD and structures (PhysicsNeMo).

  • Operational proof. ECMWF has run its machine-learning forecast system, AIFS, operationally since 2025 and publishes the data openly (ECMWF).

Three ideas transfer directly to simulation work: synthetic training data generated from your own models, surrogates for expensive inner loops such as Monte Carlo campaigns, and LLM agents that set up, run and post-process simulations through tools.

6. How and why models fail

Models fail in predictable ways: they fill gaps with plausible inventions, agree too readily, slip on arithmetic and conventions, and, as agents, sometimes satisfy the check instead of doing the work. Knowing the patterns tells you exactly where to verify.

Why they happen

A model always produces the most plausible continuation, whether or not its training data or your context contains the answer; plausible and true coincide only when the information is there. Preference training rewards answers people like, which leaks into agreeableness. Reinforcement learning rewards passing the checker, and a checker that can be gamed will occasionally be gamed.

The trend is strongly positive. Each generation confabulates less and games checks less, and labs now publish measurements such as hallucination rates. But autonomy grows faster than reliability: an agent that works for hours makes thousands of decisions, so a rare failure still shows up.

The mental model

Treat the model as a brilliant, very fast contractor who has read nearly everything, has never seen your project, cannot tell which of its memories are wrong, and will fill any gap you leave with something plausible. Give it a spec, the relevant context and a way to check its own work. Then review in proportion to the stakes.

Three security habits from day one

  • No secrets in prompts. Keep keys in environment variables, and deny agents read access to files like .env (Chapter 16 shows the rules).

  • Know your data's classification before it goes anywhere (Chapter 13).

  • Never pair broad write access with unattended web browsing. That combination is how prompt injection turns into damage.

8. Hardware: what AI actually needs

To run models yourself, two numbers decide almost everything: memory capacity sets which models fit, and memory bandwidth sets how fast they generate. Raw compute matters for reading long prompts and for image and video generation, but for chatting with an LLM, bandwidth is king. If you only use hosted models, skip to "Rent before you buy" below.

Rule 1: it has to fit

\text{weights (GB)} \approx \text{parameters (billions)} \times \frac{\text{bits per weight}}{8}

Add the KV cache from Chapter 4 and 1–2 GB of overhead. A 27B model at 4–5 bits per weight is 15–18 GB of weights, so it wants a 24 GB card for comfortable context. If a dense model does not fit, layers spill into system RAM and speed collapses; mixture-of-experts models are the exception (see expert offload below).

Rule 2: bandwidth sets speed

\text{tokens per second} \lesssim \frac{\text{memory bandwidth (GB/s)}}{\text{GB of weights read per token}}

Each generated token streams every active weight from memory once. An RTX 4090 (1,008 GB/s) running 15 GB of dense weights tops out near 67 tokens per second, and real numbers land at roughly half to three-quarters of that ceiling. MoE models read only their active experts: gpt-oss-20b, with 3.6B active parameters, decodes at about 225 tokens per second on a 4090 (runaihome). Ten tokens per second already outpaces your reading; agents want 30 or more, because they generate far more than you read.

Quantization: trading bits for memory

Quantization stores weights in fewer bits. Bits per weight below are llama.cpp's GGUF figures (llama.cpp).

The device landscape

Up means bigger models fit; right means faster generation. Only the RTX PRO 6000 and the Mac Studio M5 Ultra get near the top right, and they cost accordingly.

What each class is good for

  • NVIDIA GPU, 16–32 GB. Fastest per dollar for models up to roughly 30B dense or 35B MoE, and the default for image and video generation, where CUDA support is assumed everywhere.

  • AMD and Intel cards. More memory per dollar, such as 32 GB on the Radeon AI PRO R9700, and steadily improving software (AMD shipped official PyTorch for Windows in January 2026), but expect more setup friction, especially in image and video tools (AMD).

  • Unified memory: Mac, Strix Halo, DGX Spark. 64–512 GB runs 100B-plus MoE models at moderate speed. DGX Spark generates about 53 tokens per second on gpt-oss-120b, Strix Halo about 31 (jetsonhacks, runaihome). Prompt processing is the weak spot on Macs and Strix Halo, which hurts long agentic contexts. Windows caps Strix Halo's GPU share at 96 GB; Linux allows about 120.

  • GPU plus system RAM, with expert offload. llama.cpp can keep attention on the GPU and park MoE experts in system RAM (--n-cpu-moe), so a 16–24 GB card plus 64–128 GB of RAM runs 100B-class MoE models at usable speed. DDR5 prices more than quadrupled in eight months, though (TechSpot).

  • Multiple GPUs. llama.cpp and vLLM split models across cards. It works, but power, PCIe lanes and cooling get serious quickly; one RTX 5090 alone is rated at 575 W.

How to read a benchmark claim

  1. Which version and subset? Terminal-Bench 4.0 scores cannot be compared with 2.x, and "OSWorld" numbers come from three different subsets.

  2. Which harness? The same model scored 62.7 or 99.9 on ARC-AGI-3 depending only on the harness.

  3. Which settings? Effort level, tool access and number of attempts (pass@1 versus pass@k) all move scores.

  4. Who ran it? Sonnet 5.5 scored 70.6 on Terminal-Bench 4.0 in Anthropic's own run and 61.8 on the public board.

  5. Could the answers be in the training data? Public test sets leak; held-out and private sets deserve more trust.

  6. Is the gap bigger than the noise? Terminal-Bench 4.0 reports ±3 points, so a 1–2 point lead means nothing.

Reading a model card

  • Context window, maximum output, input and output modalities, knowledge cutoff.

  • Prices: input, output, cache writes and reads, batch discount, long-context surcharges.

  • Reasoning controls and their defaults.

  • Tool support: function calling, structured outputs, built-in server tools.

  • For open models: total and active parameters, license, recommended sampling settings, chat template, available quantizations.

Build your own eval: the best hour you will spend

  1. Collect 20–50 real tasks from your own work, each with a checkable outcome: tests that pass, numbers within tolerance, or a rubric of must-have points.

  2. Store each as a file: the prompt, the attached context, the expected result or criteria.

  3. Run every candidate model several times; outputs vary, and one lucky run proves little.

  4. Score automatically wherever possible. For prose, use a rubric with blind grading, or an LLM judge that you spot-check.

  5. Record cost and time per task next to quality.

  6. Re-run when a new model ships. Thirty minutes a quarter keeps you current.

10. Prompting and context engineering

Prompting is specification writing: the model does what a capable colleague would do with exactly the information you gave it. The newer term, context engineering, is broader: deciding everything that enters the window, including documents, examples, tools and memory.

Ten principles

  1. State the goal and the definition of done. Not "improve this code" but "reduce allocations in the inner loop of propagate(), keep the public API, and keep every test in test_propagator.cpp passing".

  2. Give the context a newcomer would need: purpose, audience, constraints, conventions, what you already tried. The model cannot ask about what it does not know it is missing.

  3. Say why. "No heap allocation after init, because this runs on a flight computer" lets the model generalize correctly to cases you never listed.

  4. Show examples. One or two samples of the output you want beat a paragraph describing it. Vary them, or the model copies their surface details.

  5. Structure with tags. Separate instructions, context, data and examples with XML-style tags such as <instructions> and <document> (prompting guide).

  6. Put long material first and the question last. Anthropic measured up to 30% better answers this way on complex multi-document inputs (long-context tips).

  7. Specify the output: length, structure, file type, or a JSON schema. For machine-read output, use structured outputs and get guaranteed valid JSON.

  8. Ask for the intermediate work you need to check: a plan before code, quotes before conclusions.

  9. Give it a way to check itself: tests to run, a reference value, a rubric. Anthropic calls this the single highest-leverage thing you can do for an agent (best practices).

  10. Iterate precisely. Treat the first answer as a draft and correct specifically: "the sign of the cross term is wrong; re-derive from equation 3."

What changed with reasoning models

  • No magic phrases. "Think step by step" is obsolete; current models reason by default, and you set the depth with the effort control.

  • Goals over procedures. Describe the outcome and constraints, let the model plan, then review the plan. Over-prescribing the method can make results worse.

  • Literal instruction-following. Modern models do what you say: ask them to "suggest changes" and they will suggest rather than edit. If you want ambitious, thorough work, ask for it explicitly.

  • Say what to do, not what to avoid. "Write in flowing paragraphs" works better than "don't use bullet points".

  • Context beats personas. "You are a world-class expert" adds little; a precise description of the task, the audience and the standard of quality adds a lot.

A template that works

<context>
Who I am, what the project is, and what matters most (accuracy, speed, readability).
Conventions: SI units; quaternions Hamilton, scalar-first; frames ENU.
</context>

<task>

</task>

</inputs>

Anything you would repeat every time belongs in standing instructions instead: a Claude Project's instructions, a CLAUDE.md file, a saved style. Keep those short, specific and current; Chapter 16 shows a CLAUDE.md for a simulation repository.

An agent fills its own context, so your job shifts to shaping what it can find. A clear README, a short instruction file, one obvious command to build and test, and small, well-scoped tasks do more than any clever wording. 11. Tools, agents, MCP, and skills: how agents actually work

An agent is a model that calls tools in a loop: it reads the context, chooses an action, the harness executes it, and the result goes back into the context until the task is done. Function calling, MCP, skills and subagents are all ways of supplying or shaping those tools.

The model never touches your files or network directly; it only emits tool calls, and the harness decides whether to run them. That is where permissions, sandboxes and approvals live.

Tool use, mechanically

Each tool is described by a name, a plain-language description and a JSON schema for its inputs. The model replies with a tool-use block; your code runs the tool and returns a tool-result block. Here is the whole loop with the Anthropic Python SDK, wrapping a hypothetical simulation executable:

import anthropic, json, subprocess

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY
tools = [{
    "name": "run_sim",
    "description": "Run the 6-DOF simulation with a JSON config; returns summary statistics as JSON.",
    "input_schema": {
        "type": "object",
        "properties": {"config": {"type": "object"}},
        "required": ["config"],
    },
}]
messages = [{"role": "user", "content": "Find the launch angle between 30 and 60 degrees that maximizes range."}]

while True:
    resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=8000,
                                  tools=tools, messages=messages)
    messages.append({"role": "assistant", "content": resp.content})
    if resp.stop_reason != "tool_use":
        break
    results = []
    for block in resp.content:
        if block.type == "tool_use":
            out = subprocess.run(["./sim", json.dumps(block.input["config"])],
                                 capture_output=True, text=True).stdout
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
    messages.append({"role": "user", "content": results})

print(next(b.text for b in resp.content if b.type == "text"))

The SDK's Tool Runner (beta) runs this loop for you; keep the manual loop when you need approvals, logging or conditional execution (Tool Runner).

MCP: one protocol for every tool

The Model Context Protocol standardizes how an AI application talks to tool providers. Write a server once and it works in Claude, ChatGPT, VS Code, Cursor and many other clients. Since December 2025 it has been governed by the Linux Foundation's Agentic AI Foundation, alongside AGENTS.md and Block's goose; Google's A2A protocol joined in August 2026 (Linux Foundation, AAIF).

  • Server primitives. Tools (actions the model can call), resources (data the application can pull into context) and prompts (templates a user can invoke).

  • Transports. stdio for a local process; Streamable HTTP for remote servers, secured with OAuth 2.1.

  • Current spec: 2026-07-28. The protocol became stateless: no initialization handshake or session ID, with each request carrying its own version and capabilities. Roots, sampling and logging are deprecated with at least 12 months' notice (changelog).

  • Extensions. MCP Apps render interactive interfaces inside the chat (official since January 2026, supported by Claude, ChatGPT, VS Code and Cursor); Tasks handle long-running jobs; the MCP Registry, still in preview, lists public servers (client matrix, registry).

A minimal local server with the official Python SDK's FastMCP interface (check the SDK's README for the current version):

from mcp.server.fastmcp import FastMCP
import pandas as pd

mcp = FastMCP("sim-tools")

@mcp.tool()
def summarize_run(path: str) -> dict:
    """Load a simulation output CSV and return min, max and mean for every channel."""
    return pd.read_csv(path).describe().loc[["min", "max", "mean"]].to_dict()

if __name__ == "__main__":
    mcp.run()  # stdio transport

Register it with Claude Code using claude mcp add sim-tools -- python sim_tools.py. The docstring is the tool description the model reads, so write it like documentation for a new colleague.

Security. An MCP server runs with your permissions, and both its tool descriptions and its outputs can carry injected instructions; tool poisoning ranks third on the OWASP MCP Top 10. Researchers also showed several coding agents starting a repository's MCP servers as soon as the folder was trusted (CSA). Install servers only from sources you trust, pin versions, give them least-privilege credentials, and review changes to .mcp.json like code.

The agentic coding workflow

Anthropic's own recommendation for Claude Code is explore, plan, code, verify (best practices). On simulation code that looks like this:

  1. Explore. "Read src/dynamics/ and explain how state propagation works. Don't change anything yet."

  2. Plan. Switch to plan mode and review the plan as you would a design review. Push back on anything vague.

  3. Implement in small steps, each with a test written first.

  4. Verify with tests, regression against golden outputs, and statistical comparison of Monte Carlo results across seeds.

  5. Review the diff yourself, then commit with a meaningful message or open a pull request.

Verification patterns for numerical code

These are classic techniques; the power move is asking the agent to build them before it changes anything.

  • Golden-file regression. Keep reference outputs from a trusted version and compare within tolerances. Never let an agent regenerate golden files without your approval; that is the classic reward hack.

  • Invariants. Energy or momentum conservation, unit quaternion norm, orthonormal rotation matrices, symmetric positive-definite covariances.

  • Analytic cases. Keplerian two-body orbits, harmonic oscillators, free fall: compare against closed-form solutions.

  • Convergence order. Halve the time step and the error should fall by the method's order; 16× for RK4.

  • Finite-difference checks of every analytic derivative.

  • Cross-implementation. Run the C++ code and the Python prototype on identical inputs.

A prompt that puts this to work: "Before touching the integrator, add a test that shows fourth-order convergence on a harmonic oscillator. Then make the change and show the test still passes."

Math with a safety net

Ask for the derivation, then ask the model to check it in code it actually runs:

import sympy as sp

x, y, xs, ys = sp.symbols("x y x_s y_s", real=True)
h = sp.Matrix([sp.sqrt((x - xs)**2 + (y - ys)**2),   # range
               sp.atan2(y - ys, x - xs)])            # bearing
H = sp.simplify(h.jacobian([x, y]))
print(H)

Follow with a NumPy finite-difference check at ten random states and a report of the maximum error. A model that derived something wrong by hand will usually catch it when forced to compute.

Data analysis

  • Give the model the schema and the first 20 rows, not the whole file, and have it write a script. Claude Code and the Claude app's code execution run the script themselves.

  • Ask for reproducibility: scripts saved in the repository, fixed random seeds, pinned versions.

  • Check for the silent errors: wrong units, dropped NaNs, misaligned timestamps, mislabeled axes.

Writing and documentation

Use AI for first drafts of design documents, test reports and code comments, and for turning rough notes into structure. Supply a template and an example of a good past document. Verify every number and claim, and never let it invent requirement IDs or results.

Learning a new domain fast

  • Tutor mode: "Teach me the unscented Kalman filter, starting from the EKF I already know. Quiz me after each step, then give me a minimal NumPy implementation to test against an EKF on a pendulum."

  • Paper reading: upload the PDF, ask for the key equations with a notation table, implement the core algorithm, then check it against the paper's figures.

What not to delegate

Acceptance decisions on safety-critical behavior stay with people. Certified software processes still apply in full: AI-written code gets the same reviews, tests and traceability as anything else. And you are the author of everything you commit, no matter who typed it.

Circuit, ruling 2–1, rejected Anthropic's challenge, leaving the Pentagon able to remove Claude from its systems and to bar contractors from using Anthropic products in their Defense Department work. The ruling is not government-wide. A separate federal court in California found this summer that the Pentagon acted unlawfully in punishing the company, and Anthropic has said it is considering further review (CP24).

The practical upshot: if your work is for the Department of Defense, check your company's current guidance before using Claude on that work in any environment, including GovCloud. The FAQ above predates these rulings, and the litigation is ongoing.

Local and air-gapped options

  • Open-weight models on approved hardware. A vLLM or llama.cpp server inside the enclave, with Open WebUI as the chat front end and coding agents such as OpenCode, Cline or Continue pointed at the local endpoint (Chapter 18). Model files move in through your approved transfer process.

  • Model provenance rules. Some organizations prohibit models from certain countries even when run offline. US and European open options include gpt-oss, Gemma 4, Meta's Muse models, NVIDIA Nemotron and Mistral. Read each license too.

  • Offline-friendly tools. llama.cpp, Ollama, LM Studio's headless mode, vLLM on Linux, Open WebUI, and ComfyUI, which gained an --offline flag in 2026 (ComfyUI changelog).

  • A capability gap to plan around. The best open models score about 20% below the frontier on composite indexes, and those that fit one GPU score lower still. Use them for drafting, explanation, completion and log parsing; keep tasks smaller and checks tighter.

Habits that keep you out of trouble

  1. Classify before you paste, and ask your security office when unsure.

  2. Keep work and personal accounts strictly separate.

  3. Ask the general question. The math, the algorithm or the library question often gets you the help you need without any program details. Confirm your policy allows even that.

  4. Strip identifiers from anything you are permitted to share.

  5. Keep an audit trail of which tool saw which data; enterprise tools log this for you.

  6. Bring your skills, not your data. Build fluency on personal and open-source projects at home, then carry the workflows (prompts, evals, agent patterns) to whatever tools are approved at work.

Settings that matter

  • Context length costs memory through the KV cache; set what you need, not the maximum.

  • KV-cache quantization to 8 bits is nearly free on Qwen models but measurably worse on some Gemma models, so test before relying on it (localbench).

  • Sampling: use the values on the model card.

  • Thinking mode: many models can switch it off; do so for quick tasks.

  • Speculative decoding: llama.cpp and LM Studio can pair a small draft model, or a model's built-in multi-token prediction, for extra speed.

Connect local models to your tools

  • Any OpenAI-compatible client can use http://localhost:11434/v1 (Ollama), http://localhost:1234/v1 (LM Studio) or http://localhost:8080/v1 (llama-server).

A 27B model on a 24 GB card handles focused coding tasks, explanations, refactors of a file or two, and document Q&A well.   4. Learn the knobs: steps, CFG, sampler and scheduler, and resolution (stay near 1 megapixel for most models).

  5. Try an edit: an input image plus an instruction.

  6. Add a LoRA, then run an image-to-video template with Wan 2.2 5B.

  7. Keep your workflows in git. They are JSON, and ComfyUI also embeds them in every PNG it saves.

Working like an engineer

  • Prompt in sentences. Models with LLM text encoders understand full descriptions of subject, setting, composition, lighting and style; the keyword lists of the SDXL era work worse.

  • Use Claude as a co-pilot: to draft and vary prompts, explain a node, or diagnose an error log pasted from the console.

  • Script it. ComfyUI runs as a local HTTP server, so a workflow exported in API format can be queued from Python for parameter sweeps and batches.

  • Mix local and cloud. Partner nodes call paid models such as Kling, Krea 3 and Google's Nano Banana from inside the same graph, and App Mode turns a finished workflow into a simple app (ComfyUI).

Read each license before commercial use, and do not generate images of real people without their consent.

20. Fine-tuning and local RAG: when and how

Reach for retrieval before fine-tuning: RAG adds knowledge, fine-tuning changes behavior. Most "teach the model our documents" problems are retrieval problems; fine-tuning earns its place when a small local model must do one narrow thing very consistently.

Which tool for which goal

GoalBest approach
Answer questions from your documentsRAG, or long context with caching for a small corpus
Follow your conventions every timeInstruction files, skills, a few examples
Emit a strict formatStructured outputs; a fine-tuned small model if it must run locally and cheaply
A small local model excellent at one narrow taskLoRA fine-tuning
Knowledge that changes dailyLive tools and retrieval
A generally smarter modelNeither: use a bigger model

Fine-tuning with LoRA

LoRA trains small low-rank adapter matrices instead of all the weights, and QLoRA does it on a 4-bit base model, so a single consumer GPU can fine-tune small models. Unsloth, Axolotl and Hugging Face's TRL are the common tools.

  1. Data first. 500–5,000 clean, varied examples beat 100,000 noisy ones. You can draft examples with a frontier model and review them by hand, but read the provider's terms before training on its outputs.

  2. Hold out an eval set (Chapter 9) and measure before and after, including a few general tasks to catch regressions.

  3. Export to GGUF and run the result in llama.cpp, Ollama or LM Studio.

Image LoRAs work the same way: a few dozen good images teach FLUX or SDXL a style, object or product, using community trainers such as kohya_ss or AI Toolkit.

A local RAG pipeline

  1. Ingest. Convert PDFs and Word files to text with a converter such as Docling or MarkItDown, then check the output on your hardest documents; equations and tables break first.

  2. Chunk by section, roughly 300–800 tokens with some overlap, keeping metadata: document, section, page, revision.

  3. Embed each chunk with a local embedding model served by Ollama or sentence-transformers.

  4. Store the vectors in Chroma, Qdrant, LanceDB or Postgres with pgvector.

  5. Retrieve with hybrid search (keyword plus vector), then rerank and keep the top 5–10 chunks.

  6. Generate with the chunks in tagged context; require citations and allow "not found in the documents".

  7. Evaluate with questions whose answers and source pages you know, scoring both retrieval hits and answer correctness.

Open WebUI has document RAG built in if you want results before building your own. And for well-organized folders, the simplest option often works best: give a local agent file search and read tools, the agentic search of Chapter 4, and skip the vector database entirely.

22. Habits of power users, cost control, and staying current

Power users stand out less for clever prompts than for habits: they give context generously, verify systematically, reuse what works, and re-check their tools every few months.

Twelve habits

  1. Try AI first on any task with a checkable outcome, then verify.

  2. Front-load context. Two minutes of context saves twenty of corrections.

  3. Keep tasks small and sessions fresh.

  4. Make verification part of the request, not an afterthought.

  5. Build reusable assets: instruction files, skills, templates, eval sets.

  6. Run work in parallel. Several sessions on independent tasks while you review the last result.

  7. Use the right model for each step: strong models to plan, cheaper ones to execute.

  8. Read every diff.

  9. Log failures. Each one becomes an eval item or a line in an instruction file.

  10. Dictate long prompts.

  11. Protect data and secrets by default.

  12. Re-evaluate quarterly with your own eval set, not with launch-day headlines.

Appendix B: Cheat sheets

Sizing rules of thumb

  • Weights: about 0.6 GB per billion parameters at 4-bit, about 1.1 GB at 8-bit, 2 GB at 16-bit.

  • Total memory: weights plus KV cache (formula in Chapter 4) plus 1–2 GB.

  • Speed ceiling: memory bandwidth divided by the gigabytes of active weights.

  • MoE: memory follows total parameters; speed follows active parameters.

  • Text: 1,000 tokens is about 750 words; 1 million tokens is about 1,500 pages.

Choosing quickly

  • Hard problem: Opus 5.5 at high effort; Fable 5.1 for long autonomous runs.

  • Everyday work: Sonnet 5.5.

  • Bulk processing: Haiku 5.5 with batching and caching.

  • Private or offline: a 27B local model on 24 GB, smaller models on less (Chapter 18).

  • Images on 8 GB: FLUX 3 Image Klein. Video on modest cards: Wan 2.2 5B.
