Chapter 16: Prompting, Retrieval, Tools, and Agents

Objectives. After this chapter you can:

  • write prompts on principle, understanding each practice as conditioning;

  • explain why writing out intermediate steps improves accuracy, and what reasoning models add;

  • build and evaluate a retrieval pipeline;

  • explain the tool-use protocol and implement an agent loop;

  • say why long autonomous tasks are hard, and choose the simplest structure that works.

16.1 The model is a component

A deployed LLM application is a system: a model, plus code that constructs its context, plus tools it can call, plus a control loop. Much of the practical progress since 2022 has come from the system around the model. This chapter covers that system, from the inside out.

16.2 Prompting as conditioning

The model samples from p(continuation | context). A prompt does not program the model. It conditions a distribution. Good prompting is choosing a context under which the desired output is the likely continuation. Each standard practice follows from that.

PracticeWhy it works
State the task, audience, format, and constraints explicitlyAnything unstated is filled in from the model's prior over what such requests usually want
Supply the relevant facts and documentsThe model knows only its training data and what is in the window
Give a few worked examplesIn-context learning (Section 13.6). Examples pin down format and edge cases more exactly than descriptions
Separate instructions from material with clear delimitersThe context is one token stream; structure helps the model tell what to follow from what to process
Say what to do when the answer is unknown or the input is malformedOtherwise the most likely continuation is a confident answer regardless
Ask for reasoning before the conclusionSection 16.3

A prompt with no examples is zero-shot; with examples, few-shot.

One discipline matters more than any technique. Prompts are hyperparameters, and their effects are statistical. A change that fixes the case in front of you may break ten others. Evaluate prompt changes on a held-out set of examples, as you would any other modeling decision (Chapter 17).

16.3 Reasoning in the open

Ask a model a multi-step word problem and demand only the final number, and it often fails. Ask it to work step by step first, and accuracy rises substantially (Wei and others, 2022; Kojima and others, 2022). This is called chain-of-thought prompting.

The explanation is architectural. A Transformer performs a fixed amount of serial computation per token: L layers, no more. A problem that needs more sequential steps than fit in one forward pass cannot be solved in the pass that emits the answer. But each generated token is another forward pass, and it can attend to everything written so far. Writing intermediate results into the context gives the model a scratchpad. Autoregressive generation turns a fixed-depth network into an iterated computation with external working memory.

Two extensions are in wide use.

Self-consistency (Wang and others, 2022). Sample several independent reasoning chains at nonzero temperature and return the majority answer. Errors are less correlated than correct answers, so voting helps (Problem 16.5).

Reasoning models. Models can be trained, largely by reinforcement learning on problems with checkable answers (Section 14.4), to produce extended reasoning before a final answer, often thousands of tokens not shown in full to the user. The reasoning budget becomes a dial: more tokens spent thinking, at more cost and latency, for higher accuracy on hard problems. This is sometimes called test-time computation.

A caution about faithfulness. The visible reasoning is text the model generated. It is not a trace of the computation that produced the answer. Experiments that bias a model toward an answer by irrelevant cues find that the stated reasoning often rationalizes the biased answer without mentioning the cue (Turpin and others, 2023). The reasoning usually helps and is usually informative. It should not be treated as a guaranteed explanation.

Checkpoint 16.1. A model with 48 layers is asked, with no scratchpad, for the result of applying a given lookup table to an input 100 times in succession. Why would you expect failure regardless of how well the model knows the table? How does a scratchpad change the situation?

16.4 Retrieval-augmented generation

Knowledge stored in the weights is frozen at the end of training, incomplete, impossible to update cheaply, and cannot be traced to a source. Retrieval-augmented generation (RAG; Lewis and others, 2020) addresses all four by fetching relevant text at query time and placing it in the context.

Offline, once:

  1. Split the documents into chunks of a few hundred tokens.

  2. Compute a vector for each chunk.

  3. Store the vectors in an index.

Online, per query:

  1. Compute a vector for the query.

  2. Find the chunks whose vectors are nearest.

  3. Build a prompt containing those chunks and the question, with an instruction to answer from them and cite them.

  4. Generate.

Figure 16.1: the upper row runs once, when the documents are indexed. The lower rows run for each question. The model sees only the chunks the search returns, so an answer can be no better than the retrieval.

Two kinds of vector.

Sparse (lexical)Dense (learned)
RepresentationWeighted word counts, such as TF-IDF or BM25The output of a neural encoder, a few hundred to a few thousand dimensions
Matches onShared wordsShared meaning, including paraphrase
Strong atRare exact terms: names, identifiers, error codesQuestions worded differently from the answer
Weak atSynonyms and paraphraseExact strings it has not learned to distinguish

Dense encoders are trained contrastively: given pairs of a query and a passage known to be relevant, pull their vectors together and push the vectors of unrelated passages away. Production systems usually combine both kinds, then apply a reranker, a slower model that reads the query and each candidate passage together and scores them more accurately.

Search. Comparing a query against every vector is exact and costs time proportional to the size of the collection. For millions of chunks, approximate nearest-neighbor indexes trade a little recall for orders of magnitude in speed.

How RAG fails. The generator can only use what the retriever returns.

  • The relevant chunk is not retrieved. The model then answers from its weights or invents.

  • The chunk is retrieved but was cut so that the needed context is in a neighbor.

  • Irrelevant chunks are retrieved and distract the model.

  • The retrieved text conflicts with what the model believes, and the model follows its belief.

Because the stages fail differently, evaluate them separately: the retriever by recall at k, the fraction of queries for which the right chunk is among the top k, and the generator by whether its answer is supported by the retrieved text.

Retrieval or a long context? With windows of a million tokens it is sometimes possible to include a whole document set and skip retrieval. That costs more per query and runs into the uneven use of long contexts noted in Section 15.7. For collections larger than the window, retrieval remains necessary.

16.5 Tools

An LLM cannot do exact arithmetic reliably, cannot see anything after its training data ends, and cannot act on the world. Tool use, also called function calling, addresses all three with one protocol.

  1. The context includes a description of each available tool: its name, what it does, and the names and types of its arguments.

  2. When the model judges a tool useful, it emits a structured request, typically JSON naming the tool and its arguments, in place of ordinary text.

  3. The surrounding program, the harness, parses the request, runs the tool, and appends the result to the context.

  4. The model continues with the result in view.

The model never executes anything. It writes a request, and ordinary code decides whether and how to carry it out. Models are fine-tuned on transcripts in this format, and constrained decoding (Section 15.6) can guarantee the request is well-formed.

The most consequential tool is code execution. A model that can write a program, run it, and read the output converts calculation and data analysis from recall into computation. Search and retrieval are tools too: RAG is the special case where the harness always calls one tool before the model speaks.

16.6 Agents

An agent is a model in a loop. It is given a goal. At each step it chooses an action, usually a tool call; the harness executes it; the result is appended to the context; the model chooses again. The loop ends when the model declares the task done or a budget runs out. Interleaving explicit reasoning with actions in this way was systematized as ReAct (Yao and others, 2022).

Figure 16.2: the model only ever reads text and writes text. The harness is ordinary code that turns the model's requests into actions and feeds the results back, and the loop continues until the model answers or a budget runs out.

Lab 16B implements the loop in about fifteen lines. That is the whole mechanism. Everything else in agent engineering is about making it reliable.

Why reliability is hard.

  • Errors compound. If each step succeeds with probability 0.95, a 20-step task succeeds with probability 0.95^20, about 0.36. Long tasks need very high per-step reliability or a way to detect and repair mistakes.

  • The context fills. Every action and observation is appended. Long tasks exhaust the window, and important early information gets diluted. Agents need to summarize, keep notes outside the context, and retrieve them.

  • Goals drift. Over many steps a model may pursue a subgoal past its usefulness, repeat itself, or declare success prematurely.

  • Actions have consequences. A wrong sentence can be ignored. A wrong file deletion cannot.

Design guidance.

  • Use the simplest structure that solves the problem. A single call is better than a fixed chain of calls, which is better than a free-running agent. Each step up buys flexibility and costs predictability.

  • Give the model ways to check its work: run the tests, re-read the file, validate against a schema.

  • Make tool descriptions precise and error messages informative. They are part of the prompt.

  • Bound the loop with budgets on steps, tokens, and time.

  • Require human approval for actions that are costly or irreversible, and run code in a sandbox.

  • Treat everything a tool returns as untrusted input. A web page or document can contain text written to hijack the agent. This is prompt injection, covered in Chapter 17.

16.7 Choosing an approach

SymptomLikely remedy
Output has the wrong format, tone, or level of detailRewrite the prompt; add examples
The model lacks facts that exist in your documentsRetrieval
The model lacks current or exact informationA search or calculation tool
Multi-step problems are answered wronglyAsk for reasoning first; use a reasoning model
The task needs many dependent steps with feedbackAn agent loop with checks
Behavior is right but too slow or too costly at volumeFine-tune or distill a smaller model (Chapter 14)
None of the above worksThe task may exceed the model; measure before building further

Lab 16A: a retriever, evaluated

import numpy as np
from sklearn.feature_extraction.text import TfidfVectorizer

text = open("input.txt").read()
passages = [p.strip() for p in text.split("\n\n") if len(p.split()) >= 20]   # speeches of 20+ words
vectorizer = TfidfVectorizer(sublinear_tf=True)
P = vectorizer.fit_transform(passages)        # (n_passages, n_terms), sparse, rows of unit length

def retrieve(query, k=5):
    q = vectorizer.transform([query])
    scores = (P @ q.T).toarray().ravel()      # cosine similarity: both sides are unit vectors
    top = np.argsort(-scores)[:k]
    return [(int(i), float(scores[i])) for i in top]

def build_prompt(question, k=3):
    context = "\n\n".join(f"[{n + 1}] {passages[i]}" for n, (i, _) in enumerate(retrieve(question, k)))
    return (f"Answer the question using only the passages below. "
            f"Cite passage numbers. If the passages do not contain the answer, say so.\n\n"
            f"{context}\n\nQuestion: {question}\nAnswer:")

def recall_at_k(k, n_words, trials=500, seed=0):
    """Query = n_words random words from a passage. Hit = that passage is in the top k."""
    rng = np.random.default_rng(seed)
    hits = 0
    for _ in range(trials):
        i = int(rng.integers(len(passages)))
        query = " ".join(rng.choice(passages[i].split(), size=n_words, replace=False))
        hits += i in [j for j, _ in retrieve(query, k)]
    return hits / trials

if __name__ == "__main__":
    print(len(passages), "passages,", P.shape[1], "terms")
    for n_words in [3, 6, 12]:
        print(f"{n_words:2d}-word queries:  recall@1 {recall_at_k(1, n_words):.2f}   "
              f"recall@5 {recall_at_k(5, n_words):.2f}")
    print(build_prompt("Who is called a traitor to the people?", k=2)[:600])

The output is the recall table in Section 16.4, followed by the start of an assembled prompt. build_prompt is the entire "augmentation" step: retrieved text, an instruction, the question.

Lab 16B: the agent loop

The loop below works with any function that maps a message list to a tool request or a final answer. A scripted stand-in is used so that the code runs without access to an LLM; Task 3 replaces it with a real one.

import ast, json, operator

def calculator(expression):
    """Evaluate arithmetic safely by walking the syntax tree."""
    ops = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
           ast.Div: operator.truediv, ast.Pow: operator.pow, ast.USub: operator.neg}
    def ev(node):
        if isinstance(node, ast.Constant): return node.value
        if isinstance(node, ast.BinOp): return ops[type(node.op)](ev(node.left), ev(node.right))
        if isinstance(node, ast.UnaryOp): return ops[type(node.op)](ev(node.operand))
        raise ValueError("unsupported expression")
    return ev(ast.parse(expression, mode="eval").body)

def run_agent(model, tools, user_message, max_steps=6):
    """The whole agent loop. `model` maps the message list to either
    {"tool": name, "args": {...}} or {"answer": text}."""
    messages = [{"role": "user", "content": user_message}]
    for _ in range(max_steps):
        reply = model(messages)
        messages.append({"role": "assistant", "content": json.dumps(reply)})
        if "answer" in reply:
            return reply["answer"], messages
        try:
            result = tools[reply["tool"]](**reply["args"])
        except Exception as e:                        # errors go back to the model as text
            result = f"error: {e}"
        messages.append({"role": "tool", "content": str(result)})
    return None, messages                             # step budget exhausted

def scripted_model(messages):
    """A stand-in for an LLM, so the loop can be run and tested without one."""
    n_tool_results = sum(m["role"] == "tool" for m in messages)
    if n_tool_results == 0:
        return {"tool": "calculator", "args": {"expression": "6 * 1e9 * 2e10"}}
    if n_tool_results == 1:
        flops = float(messages[-1]["content"])
        return {"tool": "calculator", "args": {"expression": f"{flops} / 1e14 / 86400"}}
    return {"answer": f"About {float(messages[-1]['content']):.1f} days."}

if __name__ == "__main__":
    answer, messages = run_agent(scripted_model, {"calculator": calculator},
                                 "How long to train 1e9 parameters on 2e10 tokens at 1e14 FLOP/s?")
    for m in messages:
        print(f"{m['role']:9s} {m['content']}")
    print("ANSWER:", answer)

Note three design choices in run_agent: the step budget, the conversion of tool errors into text the model can react to, and the calculator's refusal to evaluate anything but arithmetic. A tool that called Python's eval on model output would hand the model, and anyone who can influence its input, the ability to run arbitrary code.
