Unreal Engine

Unreal Engine for Simulation Engineers 201

74 min read

The second half of the study guide: engine internals, sensor physics, distributed time, and the engineering that makes an Unreal-based simulator credible. It assumes you have worked through Unreal Engine for Simulation Engineers.

#How to use this guide

201 is a 16-week program at 6–10 hours a week, built as source-reading labs plus builds. Part 1 taught you how to use Unreal for simulation; Part 2 teaches you how the parts you depend on actually work, so you can modify them, defend their outputs, and scale them.

#Prerequisites

You should have these from Part 1, or their equivalent:

  • A source-built UE 5.8 and fluency with modules, plugins and Build.cs.

  • A SimMath core stepping under both timing patterns (accumulator and lockstep).

  • A camera with asynchronous readback and a trace-based lidar.

  • A tested frames module (Unreal ↔ NED/ENU/ECEF).

  • Packaged headless runs driven from the command line.

Outside Unreal, 201 assumes GPU programming concepts (threads, groups, memory barriers; HLSL or CUDA), basic radiometry, numerical integration and stability, and multithreaded C++. Each chapter gives short primers where it leans on these.

#Method: source labs

Each chapter has a Read list (engine files and the question to answer from each), a Build list, and a Measure item. For every Read item:

  1. Set a breakpoint at the entry point and step, rather than reading statically.

  2. Draw the call sequence in your notebook.

  3. Write the answer to the chapter's question in two or three sentences.

  4. Record one measured number per chapter: a latency, a throughput, an error bound.

The measured numbers matter most. By the end you should be able to state, with evidence, how long a sensor sample takes to reach your code, how much your camera's noise model deviates from a real sensor, and whether two runs are bit-identical.

#Version and stability caveats

Part 2 works at the engine layer: the renderer, the render graph, the RHI, the physics thread, Mass and the build system. These internal APIs change between engine versions more often than the gameplay APIs Part 1 used. Code here is written against UE 5.8 and meant as a precise sketch; every chapter names the headers to check before you rely on a signature.

That engine layer is also the part least exposed to the UE6 transition, which moves gameplay programming to Verse. Renderer, RHI, physics and plugin code remain C++. Keep the habit from Part 1: simulation logic in plain C++ modules, Unreal-specific code in thin adapters.

#Chapter 1 — Inside the frame

In Part 1 you used tick groups and a delegate to step your simulation. Here you learn the machinery underneath: how FEngineLoop paces frames, how UWorld::Tick sequences work, how the tick task manager turns tick functions into a task graph, and how far the game thread can run ahead of rendering. With that, you can place your simulation step exactly where it belongs and reason about latency with numbers instead of guesses.

#The call chain

  1. GuardedMain → FEngineLoop::PreInit loads modules by loading phase, reads config and initializes the RHI.

  2. FEngineLoop::Init creates GEngine (a UGameEngine in a packaged build, UUnrealEdEngine in the editor) and starts it.

  3. Every frame, FEngineLoop::Tick runs, roughly in this order:

    1. Begin-frame bookkeeping and the BeginFrame render command.

    2. GEngine->UpdateTimeAndHandleMaxTickRate(): computes the frame delta, applies a custom time step, fixed frame rate or frame-rate cap, and sleeps if the frame is early.

    3. Platform messages and input polling.

    4. GEngine->Tick(DeltaSeconds, ...): for each world context, UWorld::Tick; then viewport drawing, which builds the view family and enqueues rendering through BeginRenderingViewFamily.

    5. Slate UI tick and draw.

    6. End-of-frame delegates and the frame-end sync that keeps the game thread from running too far ahead of the render thread.

#Inside UWorld::Tick

  1. Network tick dispatch and FWorldDelegates::OnWorldTickStart.

  2. Time update: time dilation is applied and the delta is clamped by World Settings.

  3. Level streaming update and FWorldDelegates::OnWorldPreActorTick.

  4. The tick task manager starts the frame, then runs the groups: TG_PrePhysics, TG_StartPhysics (the physics step is kicked off), TG_DuringPhysics (runs without waiting), TG_EndPhysics (waits for physics unless it runs asynchronously), TG_PostPhysics.

  5. The timer manager and FTickableGameObjects tick.

  6. Camera managers update.

  7. TG_PostUpdateWork, then TG_LastDemotable.

  8. The tick task manager ends the frame and OnWorldPostActorTick fires.

A subtle consequence for Part 1's Pattern A: in the engine versions I know, OnWorldTickStart fires before step 2, so the delta it receives is undilated and unclamped. That is arguably what you want for an accumulator, but it means slomo does not slow your simulation and hitches are not clamped for you. Confirm it in LevelTick.cpp for 5.8 (Read item 4) and decide deliberately.

#How tick functions become tasks

Every Actor and component tick is an FTickFunction. Each frame, FTickTaskManager turns the enabled ones into task-graph tasks:

  • Tick groups are barriers. A function starts no earlier than its TickGroup and must finish by its EndTickGroup (which defaults to the same group). Widening that window lets long work overlap physics.

  • Prerequisites become task dependencies. AddPrerequisite(Object, OtherTickFunction) adds a graph edge. Within a group, everything else is unordered.

  • bHighPriority asks for a function to be dispatched early within its group, which suits work that kicks off asynchronous jobs.

  • bRunOnAnyThread lets the task run on a worker thread. The function must then touch only data it owns: no UObject calls, no component transforms.

  • Intervals move a function onto a cooling-down list until its interval expires, which is why intervals align to frame boundaries.

  • Enabling or disabling a tick during a frame takes effect the next frame.

#A custom tick function for the simulation step

A dedicated tick function is a better home for the step than a delegate: it gets the dilated, clamped game delta, it can be a prerequisite for sensors, and it shows up by name in Unreal Insights and in the dumpticks console command.

// SimStepTickFunction.h
USTRUCT()
struct FSimStepTickFunction : public FTickFunction
{
    GENERATED_BODY()

    TWeakObjectPtr<USimClockSubsystem> Target;

    virtual void ExecuteTick(float DeltaTime, ELevelTick TickType,
                             ENamedThreads::Type CurrentThread,
                             const FGraphEventRef& MyCompletionGraphEvent) override
    {
        if (USimClockSubsystem* Clock = Target.Get())
        {
            Clock->AdvanceFrame(DeltaTime);
        }
    }

    virtual FString DiagnosticMessage() override { return TEXT("FSimStepTickFunction"); }
};

template<>
struct TStructOpsTypeTraits<FSimStepTickFunction>
    : public TStructOpsTypeTraitsBase2<FSimStepTickFunction>
{
    enum { WithCopy = false };   // tick functions must not be copied
};
// SimClockSubsystem.cpp
void USimClockSubsystem::OnWorldBeginPlay(UWorld& InWorld)
{
    Super::OnWorldBeginPlay(InWorld);

    StepTick.Target = this;
    StepTick.TickGroup = TG_PrePhysics;
    StepTick.bCanEverTick = true;
    StepTick.bHighPriority = true;
    StepTick.bTickEvenWhenPaused = false;
    StepTick.RegisterTickFunction(InWorld.PersistentLevel);
}

void USimClockSubsystem::Deinitialize()
{
    StepTick.UnRegisterTickFunction();   // forgetting this crashes world teardown
    Super::Deinitialize();
}

// Anywhere a sensor must run after the step in the same frame:
Sensor->PrimaryComponentTick.AddPrerequisite(Clock, Clock->GetStepTickFunction());

#How far ahead the game thread runs

The game thread prepares frame N+1 while the render thread draws frame N, and the GPU may be a frame behind that. Frame-end sync caps the lead:

  • r.OneFrameThreadLag (default on) allows the game thread one frame of lead over the render thread. Turning it off serializes them: lower latency, lower throughput.

  • r.GTSyncType chooses what the game thread syncs against: the render thread, the RHI thread, or the swap-chain flip on platforms that support it. Read its help text in your build (help r.GTSyncType in the console).

For hardware-in-the-loop work with a display, the input-to-photon latency is the sum of the game-thread frame, the render-thread frame, GPU time, compositor and display scan-out. Measure it end to end with a photodiode on the screen and a timestamped stimulus; estimates from settings are routinely off by a frame or more.

#Frame pacing

UpdateTimeAndHandleMaxTickRate decides how long to wait when a frame finishes early. It sleeps for most of the remainder and then waits out the rest, so pacing accuracy depends on the OS timer. On a desktop OS expect jitter on the order of a millisecond or less; measure it rather than assuming. If your requirement is tighter, drive time from an external clock through a custom time step (Chapter 7) instead of relying on pacing.

#Chapter 2 — UObject internals

Reflection is a runtime type database you can query: every UCLASS and USTRUCT carries a list of typed, named properties with byte offsets. Serialization, garbage collection, the editor, Blueprints and Python are all clients of that database. Used directly, it gives a simulation team generic config logging, JSON round-tripping, config diffs and versioned asset formats with very little code.

#The reflection database

  • UHT generates registration code (*.gen.cpp) that builds a UClass, UScriptStruct, UEnum or UFunction object for each reflected type at startup.

  • Each type holds a linked list of FProperty objects: name, type, byte offset, flags and, in editor builds only, metadata. Properties are FFields, not UObjects, which keeps them cheap.

  • The hierarchy mirrors C++ types: FDoubleProperty, FIntProperty, FBoolProperty, FStructProperty, FObjectProperty, FArrayProperty, FMapProperty, FEnumProperty and so on.

  • Iterate with TFieldIterator<FProperty>, address values with ContainerPtrToValuePtr, and convert any value to text with ExportTextItem_Direct.

// Flatten any reflected struct into "Path.To.Field=Value" lines
void FlattenStruct(const UStruct* Type, const void* Data, const FString& Prefix, TArray<FString>& Out)
{
    for (TFieldIterator<FProperty> It(Type); It; ++It)
    {
        const FProperty* Prop = *It;
        const void* Value = Prop->ContainerPtrToValuePtr<void>(Data);
        const FString Path = Prefix + Prop->GetName();

        if (const FStructProperty* StructProp = CastField<FStructProperty>(Prop))
        {
            FlattenStruct(StructProp->Struct, Value, Path + TEXT("."), Out);
        }
        else
        {
            FString Text;
            Prop->ExportTextItem_Direct(Text, Value, nullptr, nullptr, PPF_None);
            Out.Add(Path + TEXT("=") + Text);
        }
    }
}

// Usage: stamp a run's full configuration into its log
TArray<FString> Lines;
FlattenStruct(FSimScenarioConfig::StaticStruct(), &Config, TEXT(""), Lines);

For JSON, the JsonUtilities module already does the walk in both directions, which makes reflected structs a clean format for scenario files:

FString Json;
FJsonObjectConverter::UStructToJsonObjectString(Config, Json);          // struct -> JSON

FSimScenarioConfig Loaded;
FJsonObjectConverter::JsonObjectStringToUStruct(Json, &Loaded);         // JSON -> struct

Metadata such as ClampMin or Category exists only in editor builds. Never depend on it at runtime in a packaged build.

#Serialization

FArchive is a bidirectional stream: the same operator<< code saves or loads depending on Ar.IsLoading(). Assets, cooking, save games, undo transactions and networking all use it.

  • Tagged property serialization. UPROPERTY members are saved with name and type tags, so adding, removing or reordering properties does not break old assets. Renames need a redirect in config ([CoreRedirects] with +PropertyRedirects=(OldName="...", NewName="...")).

  • Custom versions. Register a GUID-identified version for your plugin and branch on it when loading old data.

  • Deprecated properties. A property whose name ends in _DEPRECATED is still loaded from old assets but never saved, which is exactly what a migration needs.

#Garbage collection, one level down

  • Reachability. The collector starts from roots: objects added to the root set, objects reported by FGCObjects, and engine-held references. It follows each class's reference description, generated from reflection, rather than parsing objects generically. Marking runs in parallel.

  • Purge. Unreachable objects get BeginDestroy, then FinishDestroy once IsReadyForFinishDestroy returns true (render resources may need a frame or two to release), then their memory is freed. Purging can be spread across frames.

  • Clusters. Cooked content can be grouped into GC clusters (for example a material and its textures) that the collector treats as one node, which shortens marking.

  • Garbage flag. A destroyed Actor is flagged as garbage immediately and freed at a later collection. That gap is why IsValid() beats a null check.

  • When it runs. Automatic collection happens on a timer (gc.TimeBetweenPurgingPendingKillObjects) or under memory pressure. You can force it with GEngine->ForceGarbageCollection(true).

Sim practice: collection pauses are frame-time spikes. For timing-sensitive runs, lengthen the automatic interval and force a collection at episode boundaries, such as between Monte Carlo runs or after loading a scenario, so pauses land where they cannot distort results.

#Chapter 3 — The renderer for sensor engineers

Unreal's renderer keeps a parallel render-thread copy of the world, builds each frame as a Render Dependency Graph (RDG) of passes, and lets plugins inject their own passes through scene view extensions. Once you can add an RDG compute pass that reads the scene's depth, normals and velocity, every buffer the renderer computes becomes available to your sensors without an extra scene render.

Your pass slots in after the buffers it needs already exist, so ground-truth outputs cost one compute dispatch rather than another scene render.

#Two copies of the world

Game thread (UObjects)Render thread (proxies and resources)
UWorldFScene (reached through World->Scene)
UPrimitiveComponentFPrimitiveSceneProxy, created by CreateSceneProxy()
ULightComponentFLightSceneProxy
UMaterialInterfaceFMaterialRenderProxy
UTexture, UTextureRenderTarget2DFTextureResource wrapping an FRHITexture

Rules that follow from the split:

  • The game thread never touches proxies and the render thread never touches UObjects. Data crosses only through ENQUEUE_RENDER_COMMAND lambdas that capture copies.

  • Moving a component marks its render transform dirty; the update reaches the proxy by render command. Changing render state (mesh, material, visibility flags) recreates the proxy, which is far more expensive. Avoid toggling render state every step.

  • Everything the render thread sees for frame N was enqueued by the game thread during frame N, which is why a capture triggered in TG_PostUpdateWork sees that frame's final poses.

#What one frame of rendering does

Viewport drawing calls BeginRenderingViewFamily, which enqueues a scene renderer for the view family. On the render thread, the deferred renderer builds an RDG graph: visibility and culling, depth prepass, Nanite rasterization, the base pass writing the GBuffer, shadows, lighting and Lumen, translucency, then post-processing and tone mapping.

Each USceneCaptureComponent2D creates its own scene renderer against the same FScene with its own view. That is why N captures cost roughly N scene renders: visibility, shadows and lighting are recomputed per view. It is also why a capture's show flags matter so much; every flag you turn off removes passes from its graph.

#The Render Dependency Graph

RDG is a declare-then-execute model. You describe passes and the resources they read and write; the graph culls passes whose outputs nobody uses, orders the rest, inserts GPU barriers and aliases transient memory, then executes.

  • FRDGBuilder GraphBuilder(RHICmdList) builds a graph; GraphBuilder.Execute() runs it. Inside engine hooks you are handed an existing builder.

  • Resources are handles: FRDGTextureRef, FRDGBufferRef, created with GraphBuilder.CreateTexture / CreateBuffer, or imported with RegisterExternalTexture / RegisterExternalBuffer.

  • Passes declare parameters in a shader parameter struct, and that declaration is the dependency information.

  • FComputeShaderUtils::AddPass adds a compute dispatch; AddEnqueueCopyPass copies a buffer or texture into a readback object.

  • For debugging, r.RDG.ImmediateMode 1 executes passes as they are added, so a breakpoint in a pass lambda shows a sane call stack.

#A compute shader in your plugin

    BEGIN_SHADER_PARAMETER_STRUCT(FParameters, )

#Chapter 4 — Physically based EO and IR cameras

To model a camera rather than make a picture, capture scene-referred linear radiance before tone mapping, then run your own optics, exposure, noise and readout chain in a pass you control. Validate it the way camera vendors characterize real sensors: with a photon transfer curve. Unreal supplies the radiance; everything after that should be yours.

#What Unreal gives you

  • Physical light units. Directional lights in lux, point and spot lights in candela or lumens, emissive materials and sky in luminance-like units. Scene color is linear and proportional to luminance.

  • Pre-exposure. To keep values inside 16-bit float range, the renderer scales scene color internally by the view's exposure. A linear HDR capture may therefore carry a scale factor you must remove. Find exactly where pre-exposure is applied and undone in SceneCaptureRendering.cpp for your version, and confirm with a calibration target (Build 1).

  • Physical camera exposure. Manual exposure from ISO, shutter speed and f-stop uses the standard EV100 relation, EV100 = log2(N² / t) − log2(S / 100). Use it to set capture brightness sensibly, but do not rely on Unreal's exposure and tone mapping as your sensor model.

  • RGB only. Unreal renders three broad channels, not spectra. A real sensor's channel response must be approximated by a fitted 3×3 matrix from scene RGB, which is a genuine limitation for narrowband or spectral work.

#The chain you should own

  1. Scene radiance. Capture SCS_SceneColorHDR into a 32-bit (or 16-bit) float target, with bloom, lens flares, vignetting, auto exposure and tone mapping off.

  2. Optics. Convert radiance to focal-plane irradiance with the camera equation, including cos⁴ falloff (natural vignetting), then apply distortion and blur.

  3. Signal. Convert irradiance to mean photoelectrons per pixel from exposure time, pixel area and quantum efficiency.

  4. Noise. Shot noise, dark current, read noise, and fixed-pattern noise (PRNU multiplicative, DSNU additive).

  5. Readout. Full-well clipping, analog gain, ADC with offset and bit depth, global or rolling shutter timing.

  6. ISP (optional). Bayer mosaic and demosaic, white balance, tone curve and compression, if your perception stack consumes post-ISP images.

The camera equation for on-axis-normalized irradiance at field angle θ, with lens transmission T and f-number N:

E=π L T4N2cos⁡4θE = \frac{\pi \, L \, T}{4 N^{2}} \cos^{4}\theta

Mean signal electrons for exposure time t, pixel area A and quantum efficiency η at wavelength λ:

μe=η E A thc/λ\mu_e = \eta \, \frac{E \, A \, t}{h c / \lambda}

In RGB you cannot evaluate this per wavelength, so calibrate one gain per channel from radiance to electrons against a reference (a real camera's flat-field data, or a datasheet's sensitivity at a stated illuminant).

#Noise, by the standard

The EMVA 1288 standard models a linear camera with system gain K (DN per electron), dark noise σ_d (electrons) and quantization noise σ_q. The variance of the output in DN grows linearly with mean signal:

σy2=K2σd2+σq2+K (μy−μy,dark)\sigma_{y}^{2} = K^{2}\sigma_{d}^{2} + \sigma_{q}^{2} + K\,(\mu_{y} - \mu_{y,\mathrm{dark}})

That line, plotted as variance against mean, is the photon transfer curve. Its slope is K and its intercept gives the dark noise. If your simulated camera reproduces the PTC of the real camera (or of its EMVA datasheet), your noise model is right in the way that matters.

Implementation notes:

  • Generate PRNU and DSNU maps once per simulated camera from a seed (they are fixed patterns, like a serial number), store them as textures, and reuse them every frame.

  • Use a counter-based RNG on the GPU, keyed by seed, frame index and pixel index. Every pixel's noise is then independent of thread scheduling and reproducible run to run.

  • Use a Gaussian approximation to Poisson shot noise above a few tens of electrons and an exact Poisson sampler below, or dark scenes will be wrong.

// Counter-based hashing: identical (seed, frame, pixel) -> identical noise, on any GPU schedule
uint Pcg(uint v)
{
    uint s = v * 747796405u + 2891336453u;
    uint w = ((s >> ((s >> 28u) + 4u)) ^ s) * 277803737u;
    return (w >> 22u) ^ w;
}
float U01(uint h) { return (h >> 8) * (1.0 / 16777216.0); }
float Gauss(uint k) { return sqrt(-2.0 * log(max(U01(Pcg(k)), 1e-7))) * cos(6.2831853 * U01(Pcg(k ^ 0x9E3779B9u))); }

[numthreads(8, 8, 1)]
void SensorCS(uint3 Id : SV_DispatchThreadID)
{
    const uint Key  = Pcg(Pcg(Pcg(Seed) ^ FrameIndex) ^ (Id.y * Width + Id.x));
    const float MeanE = ElectronsPerRadiance * Radiance[Id.xy].g * ExposureS * Prnu[Id.xy];

    float E = MeanE + DarkCurrentE * ExposureS + Dsnu[Id.xy];
    E += sqrt(max(MeanE, 0.0)) * Gauss(Key);          // shot noise (Gaussian regime)
    E += ReadNoiseE * Gauss(Key ^ 0x85EBCA6Bu);       // read noise
    E  = min(E, FullWellE);

    OutDn[Id.xy] = (uint)clamp(round(E * GainDnPerE + OffsetDn), 0.0, MaxDn);
}

Run the chain as a compute pass in a scene view extension on the linear scene color (Chapter 3), or on the CPU after readback while you develop it.

#Optics: distortion and blur

  • Distortion is best done with a precomputed lookup texture (often called an STMap): for every output pixel, store the source UV in the undistorted render. Build it once from intrinsics and Brown-Conrady (or fisheye) coefficients. Render the undistorted image slightly wider and at higher resolution than the output so the remap neither runs out of image nor blurs detail.

  • Blur from the lens and pixel aperture is a point-spread function. A Gaussian is a reasonable start; a measured PSF or MTF from the real lens is better. Convolve in linear radiance, before noise.

#Rolling shutter and motion blur

In a rolling-shutter sensor, row r integrates over [t₀ + r·t_line, t₀ + r·t_line + t_exp]. Three implementations, in increasing cost:

  1. Per-row rotation warp. Render once at mid-frame, then warp each row by the camera rotation accumulated over that row's time offset, using a homography K·R·K⁻¹. Exact for pure rotation, which dominates for many aerial platforms; wrong where translation creates parallax.

  2. Velocity-buffer warp. Use per-pixel motion vectors to shift each row's content by its time offset. Handles moving objects, fails at disocclusions.

  3. Banded rendering. Render k horizontal bands at k successive times with scissored captures and composite. Exact up to the band count; cost grows with k.

Motion blur follows the same pattern: accumulate several subframe renders across the exposure for a reference, and use a velocity-based approximation for real time. Unreal's motion blur is a look, not an integration over exposure time.

#Thermal infrared

Unreal has no thermal radiometry, so build it from data:

  1. Give every surface a temperature and an emissivity. Store them per instance (Custom Primitive Data or your entity registry) and drive temperatures from a thermal model in SimMath if they change.

  2. Render an ID buffer (custom stencil or instance IDs) plus depth from the IR camera pose.

  3. In a compute pass, look up each pixel's temperature and emissivity and compute band radiance: emitted plus reflected sky and surroundings, attenuated by atmospheric transmission over the pixel's range, plus path radiance.

  4. Apply the IR sensor model: optics, NETD-level temporal noise, non-uniformity, and AGC or histogram equalization if you are modeling a display image.

Spectral radiance of a blackbody (Planck's law), integrated over the sensor band (for example 8–12 µm for LWIR) and tabulated by temperature:

Lλ(T)=2hc2λ5 1ehc/(λkBT)−1L_{\lambda}(T) = \frac{2 h c^{2}}{\lambda^{5}} \, \frac{1}{e^{h c / (\lambda k_{B} T)} - 1}

Atmospheric transmission and path radiance come from an offline radiative-transfer code tabulated against range, humidity and visibility. Keep both tables in SimMath and test them independently of Unreal.

#Hardware ray tracing from a plugin

Enable hardware ray tracing in Project Settings (D3D12 or Vulkan on a ray-tracing GPU). The renderer then maintains a top-level acceleration structure (TLAS) for views that need it. For lidar you only need a hit distance, and sometimes an instance and a normal, so inline ray tracing (a RayQuery inside a compute shader) is the simplest route: no shader binding table, no hit-group shaders.

RaytracingAccelerationStructure TLAS;
StructuredBuffer<float4> BeamDirs;          // unit vectors in world orientation
RWStructuredBuffer<float> OutRangeCm;
float3 SensorOriginTranslated;              // world position + view PreViewTranslation

[numthreads(64, 1, 1)]
void LidarRayQueryCS(uint3 Id : SV_DispatchThreadID)
{
    RayDesc Ray;
    Ray.Origin    = SensorOriginTranslated;
    Ray.Direction = BeamDirs[Id.x].xyz;
    Ray.TMin      = 1.0;
    Ray.TMax      = MaxRangeCm;

    RayQuery<RAY_FLAG_FORCE_OPAQUE | RAY_FLAG_SKIP_PROCEDURAL_PRIMITIVES> Q;
    Q.TraceRayInline(TLAS, RAY_FLAG_NONE, 0xFF, Ray);
    Q.Proceed();                            // opaque-only: no candidates to resolve

    OutRangeCm[Id.x] = (Q.CommittedStatus() == COMMITTED_TRIANGLE_HIT) ? Q.CommittedRayT() : -1.0;
}

Three things to get right:

  • Translated world space. On the GPU, Unreal works in "translated world" coordinates (world position plus the view's pre-view translation) so that float precision holds in large worlds. Build ray origins in that space, or every range is off by the translation.

  • Mapping hits to entities. The query returns instance indices into the engine's GPU scene. Turning those into your entity IDs, materials or normals requires the engine's instance data. Read how the engine's own hardware ray-tracing passes resolve hits before designing your own.

  • Opacity. RAY_FLAG_FORCE_OPAQUE treats alpha-tested foliage as solid. Correct vegetation needs candidate processing with an opacity test, which is substantially more work.

The binding of the TLAS to your pass is the most version-sensitive part of this chapter. Copy the pattern from the engine's own passes in your exact version.

#The lidar return model

For an extended diffuse target that fills the beam, received power follows the lidar equation, with reflectivity ρ, incidence angle θ, receiver aperture A_r, system efficiency η and atmospheric extinction α applied over the two-way path:

Pr=Pt ρcos⁡θπ ArR2 η e−2αRP_r = P_t \, \frac{\rho \cos\theta}{\pi} \, \frac{A_r}{R^{2}} \, \eta \, e^{-2 \alpha R}

Small targets that do not fill the beam fall off faster than R⁻². From received power, model detection against background and noise: a detection probability, range noise that grows as signal-to-noise falls, dropouts on dark targets at range, and saturation or range walk on retroreflectors. Commercial sensors usually report a calibrated reflectivity or intensity rather than raw power; model the quantity your real sensor outputs.

#Beam divergence and multiple returns

A real beam is a cone. At range R with divergence δ the footprint is about R·δ wide, so one beam can straddle an edge or pass partly through foliage. Model it explicitly:

  1. Cast N sub-rays per beam across the footprint (7 or 19 in a hexagonal pattern), weighted by the beam profile.

  2. For each sub-ray hit, compute received power from the lidar equation.

  3. Build a synthetic return waveform: one pulse per sub-ray hit, placed at its range, scaled by its power.

  4. Run the real sensor's detection logic on that waveform: first, strongest or last return, with a minimum separation set by pulse width.

This produces the behaviors perception stacks must handle and simple ray casting never shows: mixed pixels at edges, ghost points between foreground and background, and multiple returns through canopy.

#Weather

  • Fog and haze: visibility V gives extinction through the Koschmieder relation, α ≈ 3.912 / V for a 2% contrast threshold. Add backscatter returns close to the sensor.

  • Rain and snow: treat drops as a random process along each beam with a size distribution; each drop can produce an early return or attenuate the beam.

  • Implement both in SimMath, applied per beam from range and conditions, so they are testable without rendering.

#Radar at three levels of fidelity

1. Object level. For each target in the field of view, compute range, angles, radial velocity and radar cross-section, then signal-to-noise from the radar equation, detection from a Swerling model, and measurement noise. Fast, and adequate for many tracking and fusion studies.

SNR=Pt Gt Gr λ2 σ(4π)3 R4 kB Ts B L\mathrm{SNR} = \frac{P_t \, G_t \, G_r \, \lambda^{2} \, \sigma}{(4\pi)^{3} \, R^{4} \, k_B \, T_s \, B \, L}

2. Ray-based scattering. Cast rays across the beam; each hit becomes a scattering center with amplitude from incidence angle and material (specular or diffuse), plus range and Doppler. Secondary bounces add multipath, such as ground reflections under vehicles. Accumulate into range-Doppler-angle cells.

3. Signal level (FMCW). From the scattering centers, synthesize the beat signal for every chirp and virtual antenna, then run the real radar's DSP chain: range FFT, Doppler FFT, CFAR detection, angle estimation. This tests the DSP itself and is how high-fidelity radar simulators work. For chirp slope S, a target at range R produces beat frequency f_b = 2SR / c; radial velocity v_r produces Doppler f_D = 2v_r / λ, visible as phase progression across chirps; angle appears as phase progression across antennas.

Target velocity at a hit point is v = v_cm + ω × r, taken from your entity registry, not from rendering. Radar cross-section comes from per-class, per-aspect tables computed offline with an electromagnetic code; Unreal supplies geometry and visibility, not electromagnetics.

#Chapter 6 — Chaos internals and coupling your own dynamics

Chaos runs on its own representation of the world, fed through a marshaling queue from the game thread and stepped by a solver that can run asynchronously at a fixed rate. Sim callbacks let your code run inside that fixed step, and contact modification lets you rewrite contacts before they are solved. Whether you couple your own dynamics through them, alongside them, or not at all is a numerical-stability decision, not a convenience one.

The physics thread can step several times per game frame, or not at all; what the game thread sees is an interpolation between results.

#Two particles per body

  • A simulated UPrimitiveComponent owns an FBodyInstance, which owns a physics proxy (FSingleParticlePhysicsProxy).

  • The proxy has a game-thread handle (GetGameThreadAPI(), an FRigidBodyHandle_External) and a physics-thread handle (GetPhysicsThreadAPI(), an FRigidBodyHandle_Internal).

  • Game-thread writes (forces, transforms, velocities, flags) mark the proxy dirty. At the start of a physics step, the solver consumes those changes.

  • After the step, results are marshaled back. With async physics, the game thread receives results stamped with simulation time and interpolates between them, so a component's transform is a blend of two physics states, not a state the solver ever produced.

That last point matters for sensors: if you read a Chaos-simulated body's pose on the game thread for a lidar or IMU, you are reading an interpolated value. Read physics-thread state, or stamp samples with the interpolation time.

#Async physics, precisely

With Tick Physics Async on, the solver advances in fixed steps of AsyncFixedTimeStepSize on the physics thread, zero or more steps per game frame. Game-thread inputs are queued with timestamps so they apply to the correct step. This is the only Chaos mode with a fixed dt independent of frame rate, which makes it the mode to use if Chaos integrates anything you care about.

#Sim callbacks

Under the convenience of AsyncPhysicsTickActor sits Chaos::TSimCallbackObject: a typed input arrives from the game thread each step, your code runs on the physics thread before integration, and a typed output goes back. The Chaos Vehicles plugin is built this way; read its manager and async callback classes before writing your own.

#Contact modification

With the contact-modification option, OnContactModification_Internal sees every contact pair after detection and before solving. For each pair you can disable it, change friction and restitution, or change the target separation. Typical simulation uses:

  • Anisotropic or slip-dependent friction for skids, tracks or simplified tires.

  • Ignoring contacts your own model already handles (for example landing gear handled by your strut model).

  • Logging contact points and normals for touch sensors or damage models.

The pair and point accessors are in ContactModification.h. Keep the work small: this runs inside the solver, on the physics thread, for every contact.

#Why force exchange goes unstable

When two solvers exchange forces once per step, each sees the other's force from the previous step. For a stiff interface (a contact, a tether, a joint split across solvers), that one-step lag behaves like an explicit integrator with a delay: below a threshold in ω·dt (ω being the interface's natural frequency) energy stays bounded, and above it energy grows every step. Fixes, roughly in order of cost:

  1. Substep the stiff side so ω·dt stays small, exchanging forces at the coarser rate.

  2. Move the stiff element into one solver so no stiff coupling crosses the boundary.

  3. Predict the interface by extrapolating the partner's state, or exchange an interface stiffness and damping instead of a bare force.

  4. Iterate within each step (implicit, strong coupling) until interface quantities converge. Accurate and stable, but each step costs several solver passes.

  5. Enforce passivity with an energy-based correction that removes injected energy at the interface.

Multi-rate schemes, such as SimMath at 1 kHz against Chaos at 120 Hz, need an explicit choice of zero-order hold or interpolation at the boundary, and a measured coupling error. Treat the interface as a numerical method in its own right.

#Chapter 7 — Time, synchronization and distributed simulation

Distributed simulation is a contract about time: who advances it, in what increments, and what each participant may assume about the others at a given instant. Choose the contract explicitly, implement it in a custom time step, and measure its latency and jitter as distributions, not averages.

#Designing a lockstep protocol properly

Part 1 built a minimal lockstep. A production protocol needs more:

  • Messages: Reset{seed, scenario}, Set{parameter, value, at_step}, Step{seq, target_step, dt_ticks}, StepDone{seq, step, sim_time_ticks, state_hash, outputs}.

  • Integer time. Express time in integer ticks (nanoseconds as int64, or step counts) on both sides. Floating-point time drifts and two sides will disagree about which step they are on.

  • Idempotency. A repeated Step with the same sequence number returns the same StepDone without stepping again, so a lost acknowledgment can be retried safely.

  • Watchdogs. Timeouts and heartbeats on both sides, with a defined behavior on expiry: stop, hold, or continue in free-run.

  • State hash in every acknowledgment. It costs microseconds and catches divergence the step it happens (Chapter 8).

  • Strict or pipelined. In strict mode the acknowledgment waits until every output for that step, including GPU readback, is ready. In pipelined mode the simulator acknowledges as soon as the step is computed and sensor data follows a couple of steps later, stamped with its step. Strict is simpler for clients; pipelined roughly doubles throughput when rendering is the bottleneck.

In the same wall time, pipelined mode completes twice as many steps here, at the cost of sensor data arriving one step behind its acknowledgment.

#FMI co-simulation

The Functional Mock-up Interface is the standard way to exchange simulation models. A model is packaged as an FMU (a zip with modelDescription.xml and binaries), and a co-simulation master advances it with fmi3DoStep (or fmi2DoStep) at communication points. FMI 3.0 adds clocks, intermediate updates and early return, all useful for event-heavy models.

Two integration directions:

  • Unreal-based simulator as master. Import FMUs (vehicle dynamics exported from Modelica or Simulink, an engine model, a battery model) into SimMath through an FMI library and step them from your clock. This is the common and tractable case.

  • Unreal as an FMU. Possible only through a shim FMU that forwards DoStep to a running Unreal process over your lockstep protocol. Useful when an existing co-simulation tool must own time.

Master algorithms matter for the same reason force exchange did in Chapter 6: Jacobi (all models step in parallel from the same inputs) is parallel but lags; Gauss-Seidel (sequential, using fresh outputs) is more stable and serial. FMUs that support getting and setting their state allow rollback and step rejection. The companion SSP standard describes how several FMUs are wired and parameterized as a system.

#HLA time management

In an HLA (IEEE 1516) federation, each federate declares itself time-regulating (its timestamped messages constrain others), time-constrained (it must never receive a message in its past), or both. A regulating federate declares a lookahead L, promising never to send a message stamped earlier than its current time plus L.

  • A federate asks to advance with a Time Advance Request. The RTI issues a Time Advance Grant only when no message stamped earlier than the requested time can still arrive.

  • Zero lookahead serializes the federation; larger lookahead allows parallelism at the cost of reaction latency.

  • Messages are delivered in timestamp order or receive order depending on how they are sent.

  • Real-time training federations often skip time management and rely on dead reckoning, DIS-style; analytic federations that run as fast as possible depend on it.

On the Unreal side the pattern is the same as lockstep: a sidecar federate talks to the RTI, and the custom time step advances when the sidecar reports a grant.

#Real time and hardware in the loop

  • Unreal is soft real time. A desktop OS, a garbage collector and a GPU pipeline do not give hard deadlines. Put the hard real-time loop (for example 1 kHz I/O with a flight computer) in a real-time target or a dedicated real-time process, and treat Unreal as a timestamped visual and sensor peripheral synchronized to it.

  • Clock synchronization. Use PTP (IEEE 1588) with hardware timestamping for sub-microsecond agreement between machines; NTP is only good to around milliseconds. Stamp every message with both simulation time and synchronized wall time.

  • Genlock and timecode. Unreal's virtual-production stack doubles as HIL infrastructure. A UTimecodeProvider supplies engine timecode, and genlocked custom time steps (UGenlockedCustomTimeStep and the implementations in the media plugins) start each frame on an external sync signal. The Timed Data Monitor plugin reports whether timestamped inputs are arriving in sync.

  • Multi-display. nDisplay renders one simulation across a cluster of machines and projectors with synchronized frame presentation, the standard approach for domes and multi-screen cockpits.

  • Late-frame policy. Decide in advance what happens when a frame misses its deadline: drop, repeat the previous output, or stall. Log every occurrence.

Write a latency budget, stage by stage, from simulation state to the device under test: step, render, readback, encode, transport, decode. Measure each stage with synchronized timestamps over hours, and judge the worst case, not the mean.

#Chapter 8 — Determinism, record/replay and checkpointing

Reproducibility is engineered, not hoped for. Hash the simulation state every step, record every input that crosses the simulation boundary, and when two runs diverge, bisect to the first differing step and the first differing field. Done well, this also changes your storage economics: you keep inputs and hashes, and regenerate sensor data on demand.

#Levels of reproducibility

LevelGuaranteeRequiresWorth it for
L0, statisticalSame distribution of outcomesSeeds loggedMonte Carlo statistics
L1, same machine and buildBit-identical state every stepFixed dt, ordered iteration, seeded RNG, no wall-clock reads, deterministic threadingRegression tests, debugging
L2, across machines, same buildBit-identical on different CPUsStrict floating-point flags, no runtime CPU dispatch in math, identical librariesCI farms, distributed batch
L3, across compilers and OSesBit-identical everywhereSoftware or fixed-point math, deterministic transcendental functionsRarely worth the cost

A realistic target: L2 for the SimMath core, L0 for rendered pixels.

#Floating point, honestly

  • Compiler modes. Fast-math modes reassociate and contract expressions, and the results change with optimization level. Compile SimMath with strict semantics (/fp:precise on MSVC; on clang, no fast-math and an explicit choice about FMA contraction with -ffp-contract).

  • Own the binary. The cleanest way to control flags is to build SimMath in its own CMake project and link it into Unreal as a precompiled external library. Your standalone tests and the engine then execute the same machine code.

  • Transcendentals. sin, exp and friends differ between C runtimes (MSVC versus glibc), which breaks L3 but not L2 on a single OS. For L3, use a correctly rounded or self-written math library.

  • Runtime CPU dispatch. Libraries that pick code paths by CPU at runtime (some BLAS and vector-math libraries) produce different bits on different machines. Disable dispatch or use the library's reproducibility mode.

  • Parallel reductions. Sums in a different order give different bits. Use a fixed partitioning with an ordered reduction tree that does not depend on thread count, or exact accumulators.

  • Denormal flags. Flush-to-zero and denormals-are-zero live in a per-thread control register. Set them explicitly on every worker thread that runs simulation math.

#State hashing

Define a canonical serialization of simulation state: entities in stable-ID order, fields in fixed order, the raw bits of each double. Hash it every step with a fast non-cryptographic hash.

// SimMath (plain C++, standalone xxHash library)
#include <xxhash.h>

uint64_t HashWorld(const World& W)
{
    XXH3_state_t* S = XXH3_createState();
    XXH3_64bits_reset(S);
    for (const Body& B : W.BodiesSortedById())
    {
        XXH3_64bits_update(S, &B.Id, sizeof(B.Id));
        XXH3_64bits_update(S, B.PosNedM.data(), 3 * sizeof(double));
        XXH3_64bits_update(S, B.VelNedMps.data(), 3 * sizeof(double));
        XXH3_64bits_update(S, B.QuatNed.coeffs().data(), 4 * sizeof(double));
        XXH3_64bits_update(S, B.RateBodyRps.data(), 3 * sizeof(double));
    }
    W.HashRngStates(S);          // RNG positions are state too
    const uint64_t H = XXH3_64bits_digest(S);
    XXH3_freeState(S);
    return H;
}

  • Hash per entity and per subsystem, then combine. When the top-level hash diverges, the sub-hashes tell you where.

  • Watch the edge cases of hashing raw bits: −0.0 and +0.0 differ, and so do NaN payloads. Either is a real difference worth knowing about.

  • Write (step, hash) pairs to a compact binary log and include the hash in every lockstep acknowledgment (Chapter 7).

#Record and replay

Treat a run as a pure function of initial state, seeds, the input stream and the build. Record exactly those:

  1. Build identity: engine and project commits, plugin versions, a hash of compiler flags, and a manifest hash of cooked content.

  2. Configuration and seeds: the full JSON stamp from Chapter 2.

  3. Input log: every external input with the step at which it was applied: controller commands, operator input, network messages, parameter changes. Never wall-clock times.

  4. Hash log: per-step hashes, plus periodic full snapshots if replays must start mid-run.

Replay feeds the same inputs at the same steps in lockstep mode and checks hashes as it goes. Two modes are worth distinguishing:

  • Open-loop replay feeds back the recorded controller outputs. The controller is not needed and nothing about it can perturb the run.

  • Closed-loop resimulation runs a new controller version against the recorded scenario. Its outputs will differ by design, so compare outcomes, not hashes.

The storage payoff: an hour of camera and lidar data runs to hundreds of gigabytes, while the input log is typically megabytes. If state is L1 or L2 reproducible, you can regenerate any sensor window on demand. Pixels may differ in the last bits if rendering is not deterministic, but the poses and the scene will be identical.

#Checkpoint and restore

  • SimMath state: your own versioned binary serialization. This is the heart of the checkpoint.

  • Unreal-side state: the entity registry, scenario-script state, sensor internal state (RNG counters, filter states, fixed-pattern maps), and any state you keep on Actors. Mark those properties SaveGame and serialize them with a save-game proxy archive:

TArray<uint8> Bytes;
FMemoryWriter Writer(Bytes, /*bIsPersistent=*/true);
FObjectAndNameAsStringProxyArchive Ar(Writer, /*bInLoadIfFindFails=*/true);
Ar.ArIsSaveGame = true;            // only UPROPERTY(SaveGame) members are written
ImuComponent->Serialize(Ar);

  • What cannot be restored exactly: Chaos solver internals (warm-start caches, island state) and rendering history (temporal anti-aliasing, Lumen). After a restore, Chaos-integrated bodies will not continue bit-identically, and images need warm-up frames. That is one more argument for owning the dynamics.

  • Branching. Checkpoints pay for themselves in Monte Carlo work: run an expensive setup once (takeoff and ten minutes of cruise, say), then branch a thousand fault injections from the checkpoint.

#Bisecting a divergence

  1. Compare the hash logs of runs A and B to find the first differing step, s.

  2. Replay both to step s − 1 from the start or the nearest checkpoint, and dump full state at s − 1 and s with field-level detail: SimMath's dump for the core, the reflection flattener from Chapter 2 for Unreal-side structs.

  3. Diff the dumps to find the first differing field. Its owner is usually your culprit.

  4. Script all of it, so that "runs diverged" becomes "step 48,211, entity 17, GyroBias.State differs" in one command.

SymptomLikely cause
Diverges at step 0 or 1Uninitialized memory, different configuration or content
Diverges at a random step on the same machineThread ordering, a wall-clock read, an unseeded RNG, container iteration order
Diverges only on other machinesFloating-point flags, C runtime math differences, runtime SIMD dispatch
Diverges after a spawn or level loadAsynchronous loading order, BeginPlay ordering
Diverges only when rendering is onSensor data fed back into the simulation with variable latency

The last row deserves emphasis. A controller that consumes camera or lidar data is only deterministic if that data arrives at a fixed step offset. Use strict lockstep, or pipelined mode with a constant, enforced latency of k steps.

For uninitialized memory, build with AddressSanitizer (Epic's Visual Studio setup lists the AddressSanitizer component) or run the standalone SimMath tests under a memory sanitizer on Linux.

#Chapter 9 — Planet- and space-scale worlds

Unreal's double-precision world reaches a default bound of 88 million km, but several subsystems still assume a nearby origin and a fixed "up". At planetary scale you manage the origin, the drift of local vertical on a round Earth, height datums and streaming around sensors. At orbital scale you split the scene into separately scaled layers. Throughout, the rule from Part 1 sharpens: ECEF in SimMath is the truth, and Unreal space is a moving local view of it.

#What Large World Coordinates do and don't cover

  • Covered: double-precision transforms and world positions, camera-relative (translated world) rendering, and double-float types in shaders (see LargeWorldCoordinates.ush). Precision near the camera is good anywhere in the world bounds.

  • Partly covered: material code that reads world position often converts to float, losing precision far from the camera. Physics and particle systems have their own precision boundaries.

  • Not covered: interactions between distant objects computed in float by some subsystem, for example a long ray or a large collision query. Precision near the viewer does not imply precision of everything everywhere.

  • Bounds: world-bounds checks remain on by default. One astronomical unit (about 150 million km) is beyond the default bound, so solar-system scenes need layered rendering regardless of precision.

#Round-Earth effects that bite simulations

  • Local vertical drifts. With a fixed georeference origin, local up tilts away from Unreal +Z by distance divided by Earth radius: about 0.9° at 100 km and 4.5° at 500 km. Anything in Unreal that assumes +Z is up (Chaos gravity, movement components, some sky and fog math) is wrong by that much.

  • Height datums. Cesium and GNSS heights are relative to the WGS84 ellipsoid. Many maps and elevation models use orthometric heights relative to the geoid. The difference, the geoid undulation, reaches roughly ±100 m. Mixing the two is one of the most common georeferencing errors; decide your datum and convert explicitly with a geoid model in SimMath.

  • Gravity and atmosphere. Compute gravity (with J2 or a full geopotential) and atmosphere in SimMath in ECEF. For rendering, use Sky Atmosphere in a planet-centered transform mode so it stays correct at altitude and when the origin moves; Cesium's sun-and-sky actor sets this up.

  • Sun direction. Compute it in SimMath from an ephemeris for the scenario time, convert to an Unreal direction through the current georeference each frame, and drive the directional light from it.

#Origin shifting

Cesium for Unreal's origin-shift component offers three modes: disabled, switching only between sub-levels, and changing the georeference itself. In the last mode the georeference origin follows the tracked Actor, keeping coordinates small and local up aligned with +Z. Actors with a globe-anchor component are moved to stay put on the globe, everything that moves must be Movable, and anything not anchored appears to jump. A distance threshold controls when shifts occur; zero shifts continuously.

What a shift means for your simulation:

  1. Every Unreal-space position and rotation changes discontinuously in one frame. If SimMath stores ECEF and the adapter recomputes each entity's Unreal transform from ECEF through the current georeference every frame, the simulation is unaffected. If anything accumulates state in Unreal space, it breaks.

  2. Sensor poses must be computed from ECEF truth and converted, never read back from components across a shift.

  3. Temporal rendering sees a jump: flag a camera cut on capture components in shift frames, and expect motion vectors to be meaningless there.

  4. Chaos bodies are teleported. Another reason not to integrate anything you care about in Chaos.

// Adapter: ECEF truth -> Unreal, recomputed every frame through the live georeference
void USimGeoAdapter::PushEntity(const SimMath::Body& B, AActor* Actor) const
{
    const FVector EcefM(B.PosEcefM.x(), B.PosEcefM.y(), B.PosEcefM.z());
    const FVector Ue = Georef->TransformEarthCenteredEarthFixedPositionToUnreal(EcefM);

    // Attitude: body->NED from SimMath, then NED->Unreal at this location (see Part 1, Ch 6)
    const FQuat AttUe = NedToUnrealAt(Ue) * SimFrames::NedToUe(ToUe(B.QuatNed));

    Actor->SetActorLocationAndRotation(Ue, AttUe, false, nullptr, ETeleportType::TeleportPhysics);
}

#Streaming for sensors

  • 3D Tiles are chosen per view by screen-space error: coarse tiles far away, fine tiles near the viewer. A sensor that is not a registered view gets whatever the player camera caused to load. Register sensor viewpoints with Cesium's camera manager so tile selection accounts for them, much as World Partition needs streaming sources on sensor platforms.

  • Tile level of detail is geometry accuracy. A long-range lidar or radar altimeter may hit a coarse tile. Tighten the screen-space error for sensor views or force a minimum level of detail in regions that matter.

  • Collision on tiles is optional and costs memory and load time. Your lidar and ground contact need it; check that collision is generated at the level of detail you assume.

  • Source data bounds accuracy. A 30 m elevation model cannot support a 10 cm lidar validation. Record the resolution and vertical accuracy of every dataset in the scenario manifest.

#Space scales

  • Orbital mechanics live in SimMath: inertial and Earth-fixed frames, time scales, propagation. Unreal renders a view.

  • Layered scenes. Render the near field (the spacecraft and anything within a few kilometers) in normal Unreal space. Render planets and moons in a scaled-space layer: positions and sizes multiplied by the same small factor, preserving angular size and direction. Render stars as a sky cube built from a star catalog with correct relative brightness.

  • Dynamic range. Sunlit surfaces in space and a star field differ by many orders of magnitude, so a correctly exposed image of a sunlit spacecraft shows no stars. That is physics, not a bug; your camera model from Chapter 4 should reproduce it.

  • Planet shadows and eclipses are outside the reach of standard shadow maps. Compute them analytically in materials or post-processing from the Sun–planet–spacecraft geometry.

UCLASS()
class USimAgentSyncProcessor : public UMassProcessor
{
    GENERATED_BODY()

public:
    USimAgentSyncProcessor()
    {
        ExecutionOrder.ExecuteInGroup = UE::Mass::ProcessorGroupNames::SyncWorldToMass;
        ProcessingPhase = EMassProcessingPhase::PrePhysics;
        bAutoRegisterWithProcessingPhases = true;
    }

protected:
    virtual void ConfigureQueries() override
    {
        Query.AddRequirement<FSimAgentIdFragment>(EMassFragmentAccess::ReadOnly);
        Query.AddRequirement<FTransformFragment>(EMassFragmentAccess::ReadWrite);
        Query.RegisterWithProcessor(*this);
    }

    virtual void Execute(FMassEntityManager& EntityManager, FMassExecutionContext& Context) override
    {
        const SimMath::AgentArrays& Agents = GetSimAgentsSnapshot();   // read-only this frame

        Query.ForEachEntityChunk(EntityManager, Context, [&Agents](FMassExecutionContext& Ctx)
        {
            const TConstArrayView<FSimAgentIdFragment> Ids = Ctx.GetFragmentView<FSimAgentIdFragment>();
            const TArrayView<FTransformFragment> Xforms = Ctx.GetMutableFragmentView<FTransformFragment>();

            for (int32 i = 0; i < Ctx.GetNumEntities(); ++i)
            {
                const int32 k = Ids[i].SimIndex;
                FTransform& X = Xforms[i].GetMutableTransform();
                X.SetLocation(SimFrames::NedToUe(ToUe(Agents.PosNedM(k))));
                X.SetRotation(SimFrames::NedToUe(ToUe(Agents.QuatNed(k))));
            }
        });
    }

private:
    FMassEntityQuery Query;
};

Mass is one of the faster-moving APIs in the engine. Query construction, ConfigureQueries and ForEachEntityChunk signatures have changed across 5.x releases, so treat this as structure and copy exact signatures from MassProcessor.h and MassEntityQuery.h in your build.

#Level of detail without corrupting results

Mass LOD typically reduces update rates and representation detail with distance from the viewer. That is exactly right for a game and dangerous for analysis: if agent behavior updates less often when the camera is far away, simulation results depend on where someone was looking.

  • Apply LOD to representation only: instanced mesh versus Actor, animation detail, visual update rate.

  • If behavior must be decimated for cost, decimate by documented rules tied to the scenario (distance to the ownship or its sensors), never to the spectator camera.

  • Test it: move the spectator camera around during a run and confirm the per-step state hash does not change (Chapter 8).

#Representation and sensors

Switching an agent between an instanced mesh and an Actor changes what sensors see. An instanced mesh may have no per-instance collision, so a trace-based lidar can see an agent at 100 m and lose it at 101 m when it changes representation. Decide what collision each representation carries, make sensor-relevant agents use consistent geometry, and test lidar returns across representation transitions.

#Determinism inside Mass

  • Processors run concurrently when their declared accesses do not conflict, so writes to shared state outside fragments race.

  • Chunk iteration order follows archetype and chunk layout, which depends on the history of creation and destruction.

  • Deferred structural changes apply at flush points whose position relative to your step must be understood.

If agents must be reproducible, keep their dynamics in SimMath (pattern B), or make processors pure per-entity functions that never read other entities' mutable state in the same phase.

#Chapter 11 — Engine forks, plugin architecture, build and deployment engineering

Treat the engine as a vendored dependency: pin it, patch it minimally and with tests, isolate your own work in layered plugins behind stable interfaces, and build, cook and deploy everything reproducibly. Teams that skip this discipline find that every engine upgrade becomes a months-long archaeology project.

#Do you need an engine fork?

Legitimate reasons to patch the engine: a bug fix not yet upstream, a renderer or physics internal you must expose, a determinism fix (for example forcing an ordered iteration), or a hook that does not exist. Try the alternatives first:

  • Delegates, subsystems, scene view extensions, custom time steps and sim callbacks cover most needs without touching engine code.

  • A plugin can add an engine module's private folder to its include paths to read internal types. It cannot link to functions the module does not export, and it breaks easily on upgrade, so treat it as a last resort before a fork.

  • An engine plugin (installed under Engine/Plugins) can be shared across projects without modifying engine modules.

#A fork workflow that survives upgrades

  • Keep it private. Mirror Epic's repository into your organization's private Git server or a private fork. Unreal's license limits who may receive engine source; check the terms before sharing engine code outside licensees.

  • Two long-lived branches: epic/5.8, pristine and tracking a release tag, and ours/5.8, carrying your patches. Each patch is one reviewed change with a test and an entry in a PATCHES.md ledger: what, why, upstream status.

  • Upgrades become a replay of the ledger onto the next epic/ branch. The ledger is what keeps that tractable, including for the eventual move to UE6.

  • Upstream what you can. Epic accepts pull requests on GitHub; every fix that lands upstream is a patch you stop carrying.

  • Distribute binaries to non-programmers as an Installed Build produced by BuildGraph from your fork, so analysts and artists never compile the engine:

RunUAT.bat BuildGraph -script=Engine/Build/InstalledEngineBuild.xml \
    -target="Make Installed Build Win64" -set:WithDDC=true -set:HostPlatformOnly=true

#Plugin architecture at scale

  • Enforce the layering from Part 1 mechanically: SimMath (no Unreal) ← SimRuntime (Engine) ← SimSensors (renderer and RHI) and SimBridge (I/O), with editor modules depending downward only and no cycles. A CI script that parses Build.cs files and fails on violations keeps it honest.

  • Optional implementations as modular features. Register implementations of an interface through IModularFeatures and discover them at runtime. A ROS 2 bridge, a DIS bridge and a file logger can then be separate plugins that a build includes or omits, with no hard dependencies between them.

  • Deprecate deliberately. Mark old APIs with UE_DEPRECATED(Version, "Use X instead"), version plugins in the .uplugin, and keep a changelog consumers can read.

  • Binary plugins built with RunUAT BuildPlugin -Plugin=... -Package=... must match the engine version and build exactly. With a custom engine, plan to ship source plugins or rebuild per engine build.

  • Content packs. Game Feature plugins can carry scenario content that loads and unloads at runtime, which suits optional terrain sets or vehicle libraries.

#Build engineering

  • Iteration time: unity builds, adaptive unity (files you are editing are excluded from unity blobs automatically), sensible precompiled headers, include-what-you-use, forward declarations, and never including monolithic engine headers.

  • Distributed compilation: UnrealBuildTool can offload compile jobs through the Unreal Build Accelerator with Horde (check which host platforms your version supports), or through Incredibuild or SN-DBS. Shader compilation can be distributed the same way.

  • Shared caches: a shared derived-data cache for shaders and cooked data is the biggest single speed-up for a team and its CI.

  • Pinned toolchains: record the exact MSVC version, Windows SDK and Linux clang toolchain in the run manifest, and build Linux binaries in containers or with Epic's matching cross-compile toolchain (found through LINUX_MULTIARCH_ROOT).

  • Static analysis and sanitizers: UnrealBuildTool can run the MSVC or clang static analyzers and build with AddressSanitizer. Run both in CI on your plugins, not just occasionally.

#Deployment

  • Containers. Epic publishes official Linux development and runtime images for each release since 4.27 on GitHub Container Registry (access requires the Epic–GitHub link); container support is still labeled Beta. The Dockerfiles live in Engine/Extras/Containers/Dockerfiles/linux, so you can build images from your own fork. Use a multi-stage build: compile and cook in the development image, copy the packaged simulation into the slim runtime image, keep development images in private registries only.

  • GPUs in containers. Use the NVIDIA Container Toolkit and offscreen Vulkan rendering, and run several instances per GPU when sensor resolution allows.

  • Batch orchestration. Part 1's manifest-and-launcher design maps directly onto a Kubernetes Job with a work queue: each worker pulls a manifest, runs one simulation, pushes outputs to object storage and reports an exit status.

  • Remote viewing. Pixel Streaming sends a running instance's frames to a browser over WebRTC, useful for watching headless server runs or sharing a scenario without installing anything.

  • Air-gapped networks. Mirror container images, derived-data caches, plugins and third-party dependencies internally, and make sure nothing in the build or runtime downloads anything.

#Data validation: catch errors before runs

Override IsDataValid on your classes, or write UEditorValidatorBase subclasses for cross-cutting rules. Validators run on save, on demand, and headless in CI through the data-validation commandlet.

EDataValidationResult USimSensorPackage::IsDataValid(FDataValidationContext& Context) const
{
    EDataValidationResult Result = Super::IsDataValid(Context);

    for (const FSimSensorSpec& S : Sensors)
    {
        const double Ratio = SimRateHz / S.RateHz;
        if (!FMath::IsNearlyEqual(Ratio, FMath::RoundToDouble(Ratio), 1e-9))
        {
            Context.AddError(FText::FromString(FString::Printf(
                TEXT("%s: rate %.3f Hz does not divide the %.1f Hz simulation rate"),
                *S.Name.ToString(), S.RateHz, SimRateHz)));
            Result = EDataValidationResult::Invalid;
        }
    }
    return Result;
}

// Project an entity's 3D box corners into the image (OpenCV camera convention)
bool ProjectBox(const FTransform& CamToWorld, const FSimIntrinsics& K,
                const FBox& LocalBox, const FTransform& BoxToWorld, FBox2D& Out)
{
    FVector Corners[8];
    LocalBox.GetVertices(Corners);
    Out = FBox2D(ForceInit);
    int32 InFront = 0;

    for (const FVector& C : Corners)
    {
        const FVector Cam = CamToWorld.InverseTransformPosition(BoxToWorld.TransformPosition(C));
        const FVector Cv(Cam.Y, -Cam.Z, Cam.X);          // Unreal camera -> OpenCV (Part 1, Ch 8)
        if (Cv.Z <= KINDA_SMALL_NUMBER) continue;
        ++InFront;
        Out += FVector2D(K.Fx * Cv.X / Cv.Z + K.Cx, K.Fy * Cv.Y / Cv.Z + K.Cy);
    }
    return InFront == 8;   // partial boxes need clipping against the near plane instead
}

#Randomization that you can query later

  • Factors: sun position and sky, weather, material parameters (albedo, roughness, wear), textures, object placement through seeded PCG graphs, distractor objects, camera intrinsics and mounting jitter, sensor noise parameters, exposure.

  • Mechanics: Material Parameter Collections for global changes, Custom Primitive Data for per-instance variation without new materials, PCG seeds for placement, your sensor models for noise.

  • Reproducibility: derive every sample's parameters from a per-sample seed and store them in the sample's metadata. You can then query "every image with sun elevation below 10° and wet roads" when a model fails, which is the whole point.

  • Random versus structured: domain randomization builds robustness; structured sampling over the operating domain builds test sets with known coverage. Keep them separate.

  • After every randomization step, wait for streaming and temporal effects to settle before capturing (Chapter 8's warm-up rule).

#Throughput

  • Pipeline the loop across frames: randomize sample N+1 while sample N is being read back and written.

  • Run several offscreen instances per GPU, read back asynchronously, and encode on worker threads. PNG encoding is often the bottleneck; consider EXR, raw buffers with fast compression, or hardware video encoding where lossy output is acceptable.

  • When realism matters more than volume, render through the Movie Render Graph with the path tracer and accept the cost.

#Measuring the sim-to-real gap

  • Train on synthetic data, test on real data, and report the gap per class and per condition.

  • Measure distribution distance between synthetic and real images (FID-style metrics) as a cheap proxy that tracks changes to rendering or randomization.

  • Ablate one randomization factor at a time to learn which ones actually matter.

  • Mix a small real set into training and measure how much synthetic data it replaces.

  • Build digital twins of recorded real scenes and compare perception outputs on paired real and synthetic data: the most direct evidence of perception-level fidelity.

#Reinforcement learning

#OpenDRIVE and OpenSCENARIO in an Unreal simulator

  • Parse in SimMath, render in Unreal. Open-source C++ libraries already parse these formats: libOpenDRIVE for road networks, and esmini's RoadManager and ScenarioEngine for roads and OpenSCENARIO XML. Link one into SimMath; generate road meshes and the lane graph from its output in the Unreal adapter.

  • Coordinate frames. OpenDRIVE uses a right-handed inertial frame with z up and may carry a georeference (a PROJ string) in its header. Map it to your ENU or ECEF frames through the frames module, never ad hoc.

  • Scenario execution. An OpenSCENARIO storyboard (stories, acts, maneuver groups, events, actions, triggers) is evaluated against simulation state every step. Keep that evaluation in SimMath so scenarios are deterministic and testable without rendering.

  • Versions matter. OpenSCENARIO 1.3.0 corrected several position and orientation calculations, so the same file can produce different trajectories in tools implementing 1.2 and 1.3. Record the standard version your player implements in every run manifest.

  • Cross-check. Run the same scenario in your simulator and in a reference player and compare entity trajectories. Any difference is either a bug or an interpretation of the standard that you should document.

#OSI: a standard sensor interface

ASAM OSI defines protobuf messages for the boundary between environment simulation and sensor models: ground truth (all objects, lanes and signs), a sensor view (ground truth from one sensor's mounting, plus inputs such as rendered images), and sensor data (detections and outputs). Sensor models packaged as FMUs that exchange OSI messages follow the OSI Sensor Model Packaging convention. Two practical uses:

  • Plug a third-party or supplier sensor model into your simulator without writing a custom adapter.

  • Expose your Unreal-rendered sensor inputs to someone else's toolchain in a form they already understand.

#Credibility: verification, validation and accreditation

  • Verification: the implementation matches the intended model (built right).

  • Validation: the model matches reality well enough for the intended use (the right model).

  • Accreditation: a formal decision that a simulation is acceptable for a specific use.

  • Uncertainty quantification: how input and model uncertainties propagate into results.

Frameworks to know:

  • NASA-STD-7009B, approved March 5, 2024, requires credibility assessment of models and simulations with effort scaled to the criticality of decisions based on them.

  • US DoD: DoDI 5000.61 sets VV&A policy, and MIL-STD-3022 provides document templates (accreditation plan, V&V plan, V&V report, accreditation report).

  • ASME V&V 10, 20 and 40 for computational mechanics, fluids and heat transfer, and medical devices.

  • Automated driving: ISO 21448 (SOTIF), ISO 34502 (scenario-based safety evaluation) and UL 4600 use simulation evidence inside safety cases, and tool-confidence rules apply to the simulator itself.

#Credibility risks specific to Unreal

  • Engine upgrades change behavior silently. Rendering, physics and streaming change between versions. Run a regression suite of sensor statistics and golden trajectories on every engine or plugin change, and accredit specific configurations, not "the simulator".

  • Rendering features built for appearance. Temporal anti-aliasing, tone mapping and auto exposure must be disabled or characterized for any sensor whose output is evidence.

  • Content is part of the model. Materials, collision, reflectivity tables and terrain data need configuration control and validation just like code.

  • Scale of the engine. Unreal's source is available, which helps, but it is too large to verify wholesale. Treat it as commercial software and verify the specific features your results depend on.

#Milestones and acceptance criteria

Set every numeric threshold you choose yourself before you start the milestone, and record it in the V&V plan.

  1. Engineering base. Engine fork with epic/ and ours/ branches and a patch ledger; an Installed Build; the CI layering check; a containerized packaged build. Accept: a clean machine builds and runs the simulation from the repository and container registry alone.

  2. Time control. The step runs in a custom tick function; strict and pipelined lockstep with sequence numbers, idempotent retries and watchdogs. Accept: fault-injection tests (dropped, duplicated and delayed messages) pass, and round-trip latency percentiles are recorded for both modes.

  3. Reproducibility. Per-step hashes, record and replay, checkpoints, the divergence bisector. Accept: L1 agreement across 20 runs on one machine and L2 agreement for SimMath state across two machines; the bisector localizes an injected fault to the right step and field.

  4. Camera chain. Calibrated linear HDR capture, optics, noise and ADC on the GPU; rolling shutter; an LWIR camera on the aerial track. Accept: photon transfer curve recovers system gain and read noise within 2% of configuration; rolling-shutter warp error below your preset threshold against banded rendering; blackbody apparent temperature correct at range.

  5. Active sensors. GPU lidar with beam divergence, the lidar equation and multiple returns; object-level radar and FMCW synthesis. Accept: multi-return behavior demonstrated on a fence and a canopy; detection range on 10% and 90% targets within your threshold of the datasheet; FMCW range-Doppler peaks in the correct bins.

  6. World. ECEF truth with origin shifting (aerial) or OpenDRIVE geometry (ground); sensor-aware streaming. Accept: after the full route, Unreal-derived ECEF matches SimMath truth within 1 cm (aerial), or lane centerlines match the reference within 1 cm (ground).

  7. Background agents. 5,000 agents with state in SimMath and presentation through Mass or instanced meshes. Accept: the per-step hash is unchanged when the spectator camera moves; lidar returns stay consistent across representation changes.

  8. Interoperability. At least one FMU in the loop through your FMI master; OSI sensor-view output; scenario import (custom or OpenSCENARIO); optional DIS output. Accept: trajectories match a reference player or a standalone FMU run within your threshold.

  9. Data or learning. Either a labeled synthetic dataset with automated alignment checks plus one sim-to-real ablation, or a controller trained through your Gymnasium wrapper with checkpoint resets. Accept: alignment checks pass on 100% of samples; the ablation or the training curve is documented with seeds.

  10. Scale and credibility. A 1,000-run Monte Carlo branched from checkpoints in containers; CI running unit, automation, golden-trajectory and engine-upgrade regression suites; a V&V plan and a credibility matrix with evidence. Accept: any run reproduces exactly from its manifest and build ID, and every row of the credibility matrix links to evidence or is explicitly marked as a limitation.
