Unreal Engine for Simulation Engineers

69 min read

A C++ study guide · 2026-10-20 ·

#How to use this guide

This is a 12-week study path at roughly 6–8 hours a week. It takes you from a first install to a fixed-step, sensor-equipped simulation that external code can drive and that you can run headless in batch.

It assumes you already know C++ well, know simulation fundamentals (integrators, reference frames, sensor models, Monte Carlo), and use Git. It assumes nothing about game development. Every chapter translates Unreal's game vocabulary into simulation vocabulary, because most Unreal material is written for game designers and buries the parts you care about.

#How each chapter is built

  • Concepts — what the system is and why it is shaped that way.

  • Code — C++ you should type out, not paste. The idioms only stick when your fingers learn the macros.

  • Sim translation — how the concept maps onto what you already do, and where the mapping breaks.

  • Pitfalls — the traps that cost simulation people days.

  • Exercises — small builds that feed the capstone in Chapter 14.

#Study habits that pay off

  1. Treat the engine source as the documentation. Epic's docs lag the code and skip edge cases. Every time you use a class, jump to its header and read the comments. You will learn more from Actor.h, World.h and LevelTick.cpp than from any tutorial.

  2. Keep a lab notebook. Write down every surprise: a property that did not replicate, a tick that ran twice, a transform that came out mirrored. Those notes become your personal pitfall list.

  3. Learn just enough Blueprint to read it. You will build in C++, but examples, plugins and coworkers use Blueprint. Being able to read a graph is required; writing large graphs is not.

  4. Build one thing end to end before going wide. A single sensor that works from tick to file is worth more than five half-working ones.

  5. Re-derive, don't trust. When a chapter states a convention (axis order, rotation sequence, units), verify it in-engine with a test before you build on it. Conventions are where simulation work quietly goes wrong.

#Chapter 1 — The mental model: what Unreal is, and what it isn't

Unreal is a real-time renderer wrapped in a game framework that runs on a variable-rate frame loop. That makes it an excellent visual and sensor layer for a simulation, and a mediocre numerical core. Most of the pain simulation engineers report comes from asking it to be the second thing.

#What Unreal gives you

  • Rendering you could not build yourself. Physically based materials, dynamic global illumination (Lumen), virtualized geometry (Nanite), many dynamic lights (MegaLights), and an offline path tracer, all in one engine.

  • A content pipeline and editor. Importers, terrain tools, procedural placement (PCG), sequencing, and a large asset marketplace (Fab). Building a believable outdoor scene takes days, not months.

  • Full C++ source. You can read and modify every line, including the renderer and physics. This is the single biggest reason it suits engineering work.

  • Collision and scene queries. Ray casts, sweeps and overlaps against the same geometry the camera sees. That is the backbone of lidar, radar and contact sensing.

  • Scale. Double-precision world coordinates since UE5, world streaming, and georeferencing through Cesium.

  • Proven sim lineage. CARLA (autonomous driving) and AirSim and its forks (aerial) are built on it, so there is open source to learn from.

#What fights you

  • Time is variable by default. Each frame advances by however long the last frame took. Nothing about the default loop is fixed-step.

  • Physics is tuned for games. Chaos favors stability and plausibility over accuracy. It is fine for collision; it is not a validated dynamics solver.

  • Determinism is best effort. Multithreading, temporal rendering, asynchronous asset streaming and wall-clock timers all leak nondeterminism.

  • Conventions differ. Centimeters, degrees, a left-handed Z-up frame, and Euler angles with their own sign rules.

  • It is huge. Millions of lines of code, long builds, a garbage-collected object system driven by macros, and binary assets that are awkward in Git.

  • Docs are shallow on internals. You will read engine source to answer most hard questions.

#Three ways to put a simulation in Unreal

  1. Embedded core (recommended to start). Your dynamics, guidance and sensor math live in a plain C++ library with no Unreal types. A thin Unreal module links it, steps it at a fixed dt from a subsystem, and pushes the resulting state onto Actors for rendering and sensing.

  2. Co-simulation. An external process owns time and state. Unreal runs in lockstep as a renderer and sensor server, advancing exactly one step per command. CARLA's synchronous mode works this way. This is the right pattern when the authoritative sim already exists, for example a validated 6DOF in another codebase.

  3. Engine-native. Everything is Actors, Components and Chaos. It is the fastest way to a demo and the hardest to verify, because your state and your integrator are inside someone else's code.

Patterns 1 and 2 share one rule: Unreal is a peripheral, not the source of truth. The simulation state is yours; Unreal observes it, draws it, and measures it.

Data flows down the module stack inside one process; commands come back through the bridge and take effect only at the step they name. Chapters 2, 5, 8 and 9 build each box.

#The UE6 factor

Epic announced in June 2026 that UE6 will merge UE5 and Unreal Editor for Fortnite and move the gameplay programming model from C++ to Verse, with a new gameplay framework called Scene Graph. Early Access is targeted for the end of 2027 and full release 12–18 months after that. Actors and Blueprints will remain in early UE6 and be deprecated later, with conversion tools.

UE 5.8, released in June 2026, is the last planned UE5 release. What this means for you:

  • Learn on UE 5.8. It is the stable target for the next several years, and everything in this guide applies to it.

  • Engine-level C++ is not going away. Rendering, the RHI, physics and plugins are C++. The part that migrates is gameplay-framework code: Actors, Components, Blueprints.

  • The embedded-core pattern is also your hedge. If your simulation math has no Unreal types in it, a framework change only touches the thin adapter layer.

#Licensing, briefly

Per Epic's licensing page, individuals and companies under $1M annual revenue use Unreal free. A company over $1M that uses it commercially, and does not ship an application to third-party end users, needs seats at $1,850 per seat per year. Shipping an application that runs engine code for outside users moves you to a 5% royalty model instead. The page has a separate FAQ entry for government organizations. Learning on your own machine as an individual is free; anything at work goes through your contracts or legal team.

#Is Unreal the right tool?

Unreal wins when you need photoreal camera sensors, large outdoor environments, or human-in-the-loop visuals. Look elsewhere when the core need is accurate contact dynamics (MuJoCo, Drake), a ROS-native robotics workflow (Gazebo), or a USD-based pipeline with GPU-accelerated sensors (NVIDIA Isaac Sim). Many serious teams pair them: a validated dynamics engine owns physics and Unreal renders.

#Modules: the unit of everything

A module is roughly a shared library. In editor builds each module is its own DLL; in monolithic shipping builds they are linked statically. Each module has a Build.cs file written in C# that declares its dependencies and compiler settings.

// Plugins/SimCore/Source/SimRuntime/SimRuntime.Build.cs
using UnrealBuildTool;

public class SimRuntime : ModuleRules
{
    public SimRuntime(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;
        CppStandard = CppStandardVersion.Cpp20;

        // Public: types from these modules appear in YOUR public headers.
        PublicDependencyModuleNames.AddRange(new[] { "Core", "CoreUObject", "Engine", "SimMath" });

        // Private: used only inside your .cpp files.
        PrivateDependencyModuleNames.AddRange(new[] { "RenderCore", "RHI", "Sockets", "Networking" });
    }
}
// Plugins/SimCore/Source/SimRuntime/Private/SimRuntimeModule.cpp
#include "Modules/ModuleManager.h"

class FSimRuntimeModule final : public IModuleInterface
{
public:
    virtual void StartupModule() override  { /* register things */ }
    virtual void ShutdownModule() override { /* unregister */ }
};

IMPLEMENT_MODULE(FSimRuntimeModule, SimRuntime)
{
  "FileVersion": 3,
  "FriendlyName": "SimCore",
  "VersionName": "0.1",
  "Modules": [
    { "Name": "SimMath",    "Type": "Runtime", "LoadingPhase": "Default" },
    { "Name": "SimRuntime", "Type": "Runtime", "LoadingPhase": "Default" },
    { "Name": "SimEditor",  "Type": "Editor",  "LoadingPhase": "PostEngineInit" }
  ]
}

Key rules:

  • Public/Private folders matter. Only headers under Public/ are visible to dependent modules.

  • Export what others call. Classes used across modules need the SIMRUNTIME_API macro (generated from the module name), exactly like __declspec(dllexport).

  • Module types: Runtime ships; Editor exists only in editor builds; Developer is for tools. Editor-only code in a runtime module will break packaging, so guard it with #if WITH_EDITOR or move it.

#Bringing in third-party libraries

Unreal compiles with RTTI and C++ exceptions off by default, and defines macros like check, verify and TEXT that collide with other code. Handle it per module:

// In the module that wraps the library
bUseRTTI = true;            // only if the library needs dynamic_cast/typeid
bEnableExceptions = true;   // only if the library throws
PublicIncludePaths.Add(Path.Combine(ModuleDirectory, "ThirdParty", "include"));
PublicAdditionalLibraries.Add(Path.Combine(ModuleDirectory, "ThirdParty", "lib", "mylib.lib"));
THIRD_PARTY_INCLUDES_START
#include <Eigen/Dense>
THIRD_PARTY_INCLUDES_END

// Windows headers: wrap them so min/max and friends don't leak
#include "Windows/AllowWindowsPlatformTypes.h"
#include <windows.h>
#include "Windows/HideWindowsPlatformTypes.h"

For a precompiled library with no Unreal code, create a module with Type = ModuleType.External; that only adds include paths and libraries.

#UnrealBuildTool and UnrealHeaderTool

  • UnrealBuildTool (UBT) reads Target.cs and Build.cs, generates IDE project files, and drives the compiler. It is the CMake of this world. You never write a Makefile.

  • Unity builds concatenate many .cpp files to compile faster. They also hide missing includes. Build your modules with unity off now and then (bUseUnity = false; in Build.cs) to keep include hygiene honest.

  • UnrealHeaderTool (UHT) runs before the compiler. It parses headers containing UCLASS, USTRUCT, UPROPERTY and similar macros and generates *.generated.h and *.gen.cpp. It understands only a subset of C++: no templated UCLASSes, no reflected types inside namespaces, no preprocessor tricks around reflected members, and the .generated.h include must be last.

#Iteration: Live Coding

Press Ctrl+Alt+F11 in the editor to recompile and patch function bodies without restarting. It is reliable for changes inside .cpp functions. It is not reliable for header changes: new members, new UPROPERTY/UFUNCTION, or changed class layout. For those, close the editor and rebuild. The older Hot Reload system is legacy; leave it off. Most corrupted-Blueprint stories trace back to patching layout changes live.

#Config files

Settings cascade from Engine/Config/Base*.ini to your project's Config/Default*.ini to per-user overrides in Saved/Config/. Expose your own settings with a UDeveloperSettings subclass; it appears in Project Settings and saves to your ini automatically. Any ini value can be overridden from the command line, which is how you will parameterize batch runs:

MySim.exe -ini:Engine:[/Script/Engine.Engine]:bUseFixedFrameRate=True

Keep simulation parameters (vehicle mass properties, sensor specs, scenario definitions) in your own version-controlled data files or UDataAssets, not scattered across ini files.

#Source control

.uasset and .umap files are binary and cannot be merged. Use Git LFS with file locking, or Perforce, which Epic uses internally. Commit Source/, Config/, Content/, Plugins/ and the .uproject; ignore Binaries/, Intermediate/, Saved/ and DerivedDataCache/.

#Chapter 3 — Unreal's C++ dialect

Unreal C++ is standard C++20 plus a reflection layer that UnrealHeaderTool generates from macros. The core skill is knowing, for every type you write, whether it lives in the UObject world (reflected, garbage collected, editor-visible) or the plain C++ world (you own its lifetime). Most crashes simulation engineers hit in their first month come from blurring that line.

#Two worlds and their naming

#A reflected class, annotated

// SimVehicleConfig.h
#pragma once

#include "CoreMinimal.h"
#include "Engine/DataAsset.h"
#include "SimVehicleConfig.generated.h"   // must be the LAST include

USTRUCT(BlueprintType)
struct FMassProperties
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, Category = "Mass", meta = (ClampMin = "0"))
    double MassKg = 1000.0;

    UPROPERTY(EditAnywhere, Category = "Mass")
    FVector InertiaDiagKgM2 = FVector(1000.0, 1500.0, 2000.0);
};

UCLASS(BlueprintType)
class SIMRUNTIME_API USimVehicleConfig : public UPrimaryDataAsset
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Vehicle")
    FMassProperties Mass;

    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Vehicle", meta = (ClampMin = "1"))
    double DynamicsRateHz = 500.0;

    UFUNCTION(BlueprintCallable, Category = "Vehicle")
    double GetTimeStepSeconds() const { return 1.0 / DynamicsRateHz; }
};

What the macros buy you:

  • Editor exposure. The data asset gets a properties panel with validation, so non-programmers can author vehicle configs.

  • Serialization. Properties save into the .uasset automatically, with versioning.

  • Garbage-collection tracking. UObject pointers in UPROPERTY members are visible to the collector.

  • Blueprint and Python access. BlueprintCallable functions and readable properties appear in scripting.

  • Runtime introspection. You can iterate a class's properties by name, which is handy for generic logging of configs.

#Creating objects and the Class Default Object

Never new or delete a UObject.

// Inside a constructor: create components as default subobjects
ASimVehicle::ASimVehicle()
{
    Body = CreateDefaultSubobject<UStaticMeshComponent>(TEXT("Body"));
    RootComponent = Body;
    PrimaryActorTick.bCanEverTick = true;
}

// At runtime
USimLogger* Logger = NewObject<USimLogger>(this);   // 'this' is the Outer

FActorSpawnParameters Params;
Params.SpawnCollisionHandlingOverride = ESpawnActorCollisionHandlingMethod::AlwaysSpawn;
ASimVehicle* V = GetWorld()->SpawnActor<ASimVehicle>(VehicleClass, SpawnTransform, Params);

// Inject configuration BEFORE BeginPlay runs
ASimVehicle* V2 = GetWorld()->SpawnActorDeferred<ASimVehicle>(VehicleClass, SpawnTransform);
V2->Config = MyConfig;
V2->FinishSpawning(SpawnTransform);

The crucial surprise: every UCLASS constructor runs at engine startup to build the Class Default Object (CDO), the template that instances are copied from. So constructors set defaults and create subobjects, nothing else. No world access, no file I/O, no simulation logic. Put that in BeginPlay, PostInitializeComponents or a subsystem's Initialize.

#Garbage collection

Unreal uses mark-and-sweep reachability from a root set. The collector can only see a UObject pointer if it is:

  1. a UPROPERTY member (raw UFoo* or, preferably in UE5, TObjectPtr<UFoo>), including inside UPROPERTY containers;

  2. reported by a non-UObject owner that derives from FGCObject; or

  3. held in a TStrongObjectPtr<UFoo>.

Anything else can be collected out from under you, leaving a dangling pointer that crashes minutes later.

// BUG: invisible to GC. Works until the next collection, then dangles.
class FSimBridge
{
    USimVehicleConfig* Config = nullptr;
};

// FIX: a plain C++ owner reports its references
class FSimBridge : public FGCObject
{
public:
    TObjectPtr<USimVehicleConfig> Config;

    virtual void AddReferencedObjects(FReferenceCollector& Collector) override
    {
        Collector.AddReferencedObject(Config);
    }
    virtual FString GetReferencerName() const override { return TEXT("FSimBridge"); }
};

Related tools:

  • TWeakObjectPtr<T> holds a reference that does not keep the object alive; check it with .IsValid() or .Get().

  • IsValid(Obj) returns false for null and for objects already marked for destruction. Prefer it over != nullptr.

  • The console command gc.CollectGarbageEveryFrame 1 forces a collection every frame. Turn it on in testing; it turns rare GC bugs into immediate ones.

Sim translation: never create and destroy UObjects in your high-rate loop. GC cost scales with the number of objects and can cause frame hitches. Keep per-step data in plain structs and preallocated TArrays; reserve UObjects for long-lived things like vehicles, sensors and configs.

#Chapter 4 — The framework: World, Actors, Components, Subsystems

Unreal models everything as a World full of Actors built from Components, updated by a tick system that orders work within each frame. For simulation the pieces that matter most are the World, Subsystems (your simulation managers), Components (your sensors and adapters) and tick groups. Most of the rest of the "gameplay framework" can be minimized.

#The containment hierarchy

  • UEngine — one per process (GEngine). Owns the main loop.

  • UGameInstance — lives for the whole session and survives map changes.

  • UWorld — the simulation space. Owns the levels, the physics scene, the render scene, timers and the tick manager. The editor can hold several worlds at once: the editor world, a Play-In-Editor (PIE) copy, preview worlds for thumbnails.

  • ULevel — the persistent level plus streamed sublevels or World Partition cells.

  • AActor — anything that exists in the world. An Actor has no transform of its own; it uses its root component's.

  • UActorComponent — behavior with no transform.

  • USceneComponent — adds a transform and parent/child attachment.

  • UPrimitiveComponent — adds geometry for rendering and/or collision: static meshes, skeletal meshes, collision shapes.

Each box owns the one below it; dashed links show where your own code attaches. The world subsystem is the anchor for everything scenario-wide.

#Chapter 5 — Time and tick: making Unreal behave like a simulator

This is the most important chapter. By default Unreal advances by whatever wall-clock time the last frame took, so nothing is fixed-step and nothing repeats exactly. You fix that by choosing who owns time (your code, the engine at a fixed rate, or an external master), then stepping your simulation on an integer step counter that is independent of frames.

#How time flows through a frame

  1. The engine measures wall-clock time since the last frame. A custom time step, if installed, can override this.

  2. That raw delta is clamped (World Settings MaxUndilatedFrameTime caps long frames) and scaled by time dilation. The result is the frame's game delta.

  3. UWorld::Tick runs the tick groups with that delta: pre-physics, physics, post-physics, timers and tickables, post-update.

  4. The game thread hands the frame to the render thread, which runs one frame behind; the GPU may run another frame behind that.

Two consequences surprise people. A long hitch silently loses time to the clamp, so game time drifts from wall time. And the image you capture in a frame reflects state the render thread received, not necessarily the state at the instant you queried it.

The game thread moves on to the next frames while the render thread and GPU finish this one, so every sensor buffer must carry the step index it was triggered at.

#Pattern A: the fixed-step accumulator (embedded core)

Step your plain-C++ core at its own fixed rate inside a hook that runs before any Actor ticks, then push interpolated state to Actors for rendering.

void USimClockSubsystem::AdvanceFrame(double FrameDt)
{
    Accumulator += FrameDt;
    int32 StepsThisFrame = 0;

    while (Accumulator >= StepDt && StepsThisFrame < MaxStepsPerFrame)
    {
        Core->Step(StepDt);                        // plain C++, no Unreal types
        ++StepIndex;
        SimTime = static_cast<double>(StepIndex) * StepDt;   // no accumulated rounding
        OnSimStep.Broadcast(StepIndex, SimTime);
        Accumulator -= StepDt;
        ++StepsThisFrame;
    }

    if (StepsThisFrame == MaxStepsPerFrame)
    {
        UE_LOG(LogSim, Warning, TEXT("Falling behind real time; dropping %.3f s"), Accumulator);
        Accumulator = 0.0;   // or keep it and catch up, depending on your requirement
    }

    const double Alpha = Accumulator / StepDt;      // 0..1 between previous and current state
    PushInterpolatedStateToActors(Alpha);
}

The trajectory is now deterministic: the core sees the same dt sequence regardless of frame rate, as long as inputs are applied by step index rather than by frame. What is not deterministic is which steps get rendered, because frames land at arbitrary points between steps. Timestamp any frame-based sensor sample as SimTime - (1 - Alpha) * StepDt, the time of the interpolated state it actually saw.

#Pattern B: lockstep (batch runs and co-simulation)

Make every engine frame correspond to exactly k simulation steps. Then every rendered frame has a known simulation time and sensors become reproducible in timing.

For a standalone batch run, use the fixed time step with an engine dt of k × StepDt and run uncapped. For an external master, install a custom time step that blocks until the master says "advance":

#Where Chaos physics fits

If you let Chaos integrate anything, its step size matters too:

#Chapter 6 — Frames, units and precision

Unreal's world frame is left-handed with +X forward, +Y right and +Z up, measured in centimeters. If you lay +X along North and +Y along East, Unreal is NED with Z flipped and scaled by 100, and FRotator's (Pitch, Yaw, Roll) equal the aerospace 3-2-1 Euler angles. Every claim in this chapter comes with a test; run them before you build on any of it.

#Unreal's conventions

  • Length: 1 unit = 1 cm. Default gravity is −980 cm/s² along −Z.

  • Axes: +X forward, +Y right, +Z up. Left-handed.

  • Angles: FRotator stores Pitch (about Y), Yaw (about Z) and Roll (about X) in degrees, applied roll first, then pitch, then yaw about fixed axes. That is the same order as aerospace yaw-pitch-roll.

  • Signs: positive Yaw turns +X toward +Y (nose right, clockwise seen from above). Positive Pitch raises the nose. Positive Roll lowers the right side.

#The mapping that makes this easy

With +X = North, +Y = East, +Z = Up, the reflection S = diag(1, 1, −1) takes Unreal to NED. Positions, velocities and accelerations map as NED = S · UE / 100. Body axes map the same way (Unreal's body +Z is up; aerospace body z is down), so the attitude matrix maps as R_NED = S · R_UE · S.

Working that through Unreal's rotation matrix gives a useful result: with this world layout, FRotator(Pitch, Yaw, Roll) in degrees equals the aerospace Euler angles (θ, ψ, φ) of an x-forward, y-right, z-down body relative to NED. Exercise 1 makes you verify it.

#The trap: FRotator signs versus rotation vectors

FQuat, FMatrix and physics angular velocity use ordinary right-hand-rule component math (v = ω × r). Under that math, FRotator's positive Pitch and positive Roll are negative rotations about +Y and +X. You can see it in FRotator::Quaternion(), where the pitch and roll terms carry minus signs.

Two consequences:

  1. Building an FQuat from an axis and angle and expecting it to match an FRotator with the same number will be wrong for pitch and roll.

  2. Body rates: with ω the physics angular velocity expressed in Unreal body axes (rad/s), the aerospace body rates are (p, q, r) = (−ωx, −ωy, +ωz). Angular velocity is a pseudovector, so under the reflection it picks up an extra sign: ω_NED = −S · ω_UE.

#A conversion module

Put every conversion in one place in SimMath (or a thin header in SimRuntime) and test it exhaustively. Nothing else in your code should know which way Unreal's Z points.

// SimFrames.h — world laid out with UE +X = North, +Y = East, +Z = Up
namespace SimFrames
{
    constexpr double CmToM = 0.01;
    constexpr double MToCm = 100.0;

    // Positions, velocities, accelerations
    inline FVector UeToNed(const FVector& Ue)  { return FVector(Ue.X, Ue.Y, -Ue.Z) * CmToM; }
    inline FVector NedToUe(const FVector& Ned) { return FVector(Ned.X, Ned.Y, -Ned.Z) * MToCm; }

    // Attitude: R_ned = S * R_ue * S. For a quaternion (x, y, z, w) that is (-x, -y, z, w).
    inline FQuat UeToNed(const FQuat& Q) { return FQuat(-Q.X, -Q.Y, Q.Z, Q.W); }
    inline FQuat NedToUe(const FQuat& Q) { return FQuat(-Q.X, -Q.Y, Q.Z, Q.W); }  // S is its own inverse

    // Body rates from UE angular velocity expressed in UE body axes (rad/s)
    inline FVector UeBodyRateToPqr(const FVector& W) { return FVector(-W.X, -W.Y, W.Z); }
}
// Getting body-axis angular velocity from a physics body
const FVector OmegaWorld = Body->GetPhysicsAngularVelocityInRadians();   // world axes, rad/s
const FVector OmegaBody  = Body->GetComponentQuat().UnrotateVector(OmegaWorld);
const FVector Pqr        = SimFrames::UeBodyRateToPqr(OmegaBody);

Rules that prevent most frame bugs:

  • Never convert Euler angles directly between conventions. Convert vectors with S, rotations as quaternions or matrices, and produce Euler angles only at the edges with functions you have tested.

  • Normalize with FRotator::GetNormalized() before comparing angles; values outside ±180° are legal.

  • Expect gimbal-lock behavior near ±90° pitch in any FRotator conversion. Keep attitude as quaternions internally.

#IMU sanity check

At rest in a level attitude, the specific force is f = a − g = (0, 0, +980) cm/s² in Unreal. Mapped to NED body axes that is (0, 0, −9.80) m/s², which is what a real z-down accelerometer reads. If your simulated IMU says +9.8 on z at rest, a sign is wrong somewhere.

#Precision and Large World Coordinates

UE5 made FVector, FTransform and world positions double precision. Rendering stays precise by working relative to the camera in tiles, and some subsystems (mesh vertex data, most shader math, parts of physics) still use float relative to a nearby origin. This is why the old advice to keep everything near the origin has relaxed, but not vanished.

Practical guidance:

  • Your own state should be double, always. Treat any float on the path from your sim to a sensor as a precision budget item.

  • For flights over hundreds of kilometers, use origin shifting (Cesium provides an origin-shift component) so that the active region stays near the origin.

  • World Settings has a Kill Z height and world-bounds checks that destroy Actors outside them. Adjust or disable both for high-altitude, deep or very large scenarios.

  • Unreal's gravity is a constant vector along world −Z. Far from a georeference origin, world −Z is no longer local down. If you own the dynamics this does not matter; if Chaos integrates bodies, disable its gravity and apply your own.

#Geodesy

  • Keep WGS84 math (geodetic ↔ ECEF ↔ local tangent frames) in SimMath, written by you or taken from a library such as GeographicLib, and tested against known values.

  • Cesium for Unreal's ACesiumGeoreference places a chosen longitude, latitude and height at the Unreal origin, with Z up there. The globe is a true ellipsoid, not a map projection. Its transform functions take vectors ordered (longitude, latitude, height), which is the opposite of how most engineers write it.

  • Unreal also ships a Georeferencing plugin with projected coordinate systems and flat or round planet modes. Pick one georeferencing authority per project and route every conversion through it.

#Chapter 7 — Physics and vehicle dynamics

Use Chaos for what it does well: collision geometry, scene queries, and contact for objects whose motion you never need to verify. Drive your own vehicles kinematically from dynamics you control and can validate. Let Chaos integrate a vehicle only when game-grade fidelity is acceptable for the question you are answering.

#What Chaos provides

Chaos replaced PhysX in UE5. It covers rigid bodies, constraints, collision shapes (primitives, convex hulls, triangle meshes for static geometry), scene queries (ray casts, sweeps, overlaps), wheeled vehicles, destruction, cloth and fields. Its iterative solver is tuned for stability at game step sizes. That is the right trade for a game and the wrong one for a validated model.

#Kinematic drive from your own dynamics

The adapter converts SimMath state at the boundary and applies it with no sweep:

// Called from the clock subsystem after each frame's simulation steps
void ASimVehicle::ApplySimState(const SimMath::BodyState& Prev,
                                const SimMath::BodyState& Curr, double Alpha)
{
    const FVector PosNed = FMath::Lerp(ToUe(Prev.PosNedM), ToUe(Curr.PosNedM), Alpha);
    const FQuat   AttNed = FQuat::Slerp(ToUe(Prev.QuatNed), ToUe(Curr.QuatNed), Alpha);

    SetActorLocationAndRotation(SimFrames::NedToUe(PosNed),
                                SimFrames::NedToUe(AttNed),
                                /*bSweep=*/false, nullptr,
                                ETeleportType::TeleportPhysics);
}

ToUe here just copies Eigen (or your own) types into FVector and FQuat without changing frames; SimFrames handles the frame change. Keeping those two steps separate keeps both testable.

Teleport versus non-teleport moves changes whether Chaos treats the move as a jump or as motion with velocity, which matters when simulated debris should be pushed by your vehicle. Test which one your scenario needs.

#Collision queries for your own contact models

Your dynamics can still use Unreal's geometry for contact. Landing gear, wheels and skids become ray casts or sweeps against the world each step, and the hit data feeds your spring-damper or tire model.

bool USimGroundContact::QueryStrut(const FVector& MountUe, const FVector& DownUe,
                                   double MaxLengthCm, FStrutContact& Out) const
{
    FCollisionQueryParams Params(SCENE_QUERY_STAT(SimStrutTrace), /*bTraceComplex=*/true);
    Params.AddIgnoredActor(GetOwner());
    Params.bReturnPhysicalMaterial = true;

    FHitResult Hit;
    const FVector End = MountUe + DownUe * MaxLengthCm;
    if (!GetWorld()->LineTraceSingleByChannel(Hit, MountUe, End, ECC_GameTraceChannel1, Params))
    {
        return false;   // strut fully extended, no contact
    }

    Out.CompressionM = (MaxLengthCm - Hit.Distance) * 0.01;
    Out.NormalUe     = Hit.ImpactNormal;
    Out.Material     = Hit.PhysMaterial.Get();   // friction, surface type
    return true;
}

Things to set up once per project:

  • Custom trace channels. Project Settings → Collision lets you add channels such as SimGround and SimLidar (they appear in code as ECC_GameTraceChannel1, 2, ...). Then decide per object type what blocks which channel. Vegetation might block lidar but not landing gear.

  • Simple versus complex collision. Simple collision is primitive shapes and convex hulls; complex collision is the mesh's triangles. bTraceComplex = true traces against triangles, which you want for ground contact and lidar accuracy. Check that what your traces hit matches what the camera sees.

  • Physical materials. A UPhysicalMaterial carries friction, restitution and a surface type. The surface type is also a convenient hook for sensor properties such as lidar reflectivity or radar cross-section.

  • Sweeps and overlaps. SweepSingleByChannel with an FCollisionShape finds first contact along a path; OverlapMultiByChannel finds everything inside a volume. When a sweep starts in penetration, FHitResult::bStartPenetrating and PenetrationDepth tell you by how much.

#If you let Chaos integrate

  • Units. A force of 1 N is 100 kg·cm/s² in Unreal, and 1 N·m of torque is 10,000 kg·cm²/s². Multiply accordingly in your adapter. This is the most common physics bug in sim ports.

  • Mass properties. Chaos derives mass and inertia from collision geometry and density. You can override mass, nudge the center of mass and scale inertia; setting an arbitrary full inertia tensor needs physics-thread access to the Chaos particle.

  • Defaults that aren't physics. Bodies get linear damping by default, and Physics settings clamp maximum angular velocity and depenetration velocity. A spinning rotor or tumbling projectile can hit those limits silently. Zero the damping and raise the clamps deliberately.

  • Sleeping. Slow bodies go to sleep and stop being simulated. Adjust the sleep family or threshold for anything that moves slowly but must keep moving.

  • Fast movers. Enable continuous collision detection (bUseCCD) for small, fast objects or they will tunnel through thin geometry.

  • Gravity. Disable it per body and apply your own if you need anything other than a constant −9.8 m/s² along world −Z.

  • Step size. Revisit Chapter 5: with variable dt, a Chaos-integrated body is not reproducible.

#Chaos Vehicles

UChaosWheeledVehicleMovementComponent models engine torque curves, transmission, differential, ray-cast or sweep suspension and a simplified tire. It is good enough for background traffic and driver-in-the-loop work; CARLA 0.10 uses it. It is not a substitute for a validated vehicle model with a proper tire formulation.

#Bringing your own engine

The embedded-core pattern works with any dynamics library: your own 6DOF, JSBSim for flight dynamics, MuJoCo or Drake for articulated robots, Project Chrono for terramechanics. Link it into SimMath or a sibling module, step it from your clock, and push transforms out. Unreal then only renders and senses. Check each library's repository for existing Unreal integration examples before writing your own.

#Pitfalls

  • Forgetting the ×100 and ×10,000 unit factors for force and torque.

  • Default damping and angular-velocity clamps distorting results.

  • Bodies falling asleep mid-scenario.

  • Setting transforms every frame on a body Chaos is also simulating, so the two fight.

  • Traces hitting simple collision while the camera sees detailed geometry.

#Chapter 8 — Sensor simulation

Unreal gives you two sensing primitives: render the scene from a viewpoint (cameras, depth, segmentation, anything a shader can compute) and query the collision world (lidar, radar, rangefinders, contact). Most of the craft is in timing, readback and turning off the parts of the renderer that exist to look good rather than to be right.

Intrinsics. For a W × H capture with horizontal field of view h: fx = fy = (W / 2) / tan(h / 2), cx = W / 2, cy = H / 2. For an off-center principal point or a non-standard projection, set bUseCustomProjectionMatrix and supply CustomProjectionMatrix.

Camera axes. An Unreal camera looks along its +X with +Y right and +Z up. An OpenCV camera looks along +z with +x right and +y down. So x_cv = Y_ue, y_cv = −Z_ue, z_cv = X_ue. Put this in your frames module next to the NED mapping.

Anti-aliasing and temporal effects. TSR and TAA blend information across frames, and Lumen accumulates lighting over several frames. Both make a frame depend on its history, which breaks reproducibility and smears the first frames after a teleport. For ground-truth sensors use FXAA or no anti-aliasing (r.AntiAliasingMethod), and after any discontinuous camera move either warm up for several frames or accept and flag the artifacts.

Lens effects and noise. Unreal renders an ideal pinhole. Model distortion by rendering slightly wider and remapping with your Brown-Conrady (or fisheye) parameters in a post-process material or after readback; the Camera Calibration plugin's lens-distortion models, built for virtual production, are another starting point. Add shot noise, read noise, fixed-pattern noise and quantization after readback with a seeded RNG, so noise is reproducible and separable from the render.

#Getting pixels to the CPU without stalling

The simple path, RenderTarget->GameThread_GetRenderTargetResource()->ReadPixels(Out), flushes rendering and blocks the game thread until the GPU catches up. It is fine for your first exercise and ruinous for throughput.

The production path copies the render target into a staging buffer and reads it frames later:

Capture->CaptureScene();

    [Rt, Readback](FRHICommandListImmediate& RHICmdList)
    {
        Readback->EnqueueCopy(RHICmdList, Rt->GetRenderTargetTexture());
    });

PendingReadbacks.Add({ Readback, StepIndex, SimTime, CameraPoseNed });

// Later frames: poll on the render thread
ENQUEUE_RENDER_COMMAND(SimCamPoll)(
    [this](FRHICommandListImmediate& RHICmdList)
    {
        // For each pending readback whose IsReady() is true:

CaptureSceneDeferred() is cheaper because it renders alongside the main view, but then your copy must be queued after the main scene render, for example from an end-of-frame delegate. Data typically arrives one to three frames after the capture, so every buffer carries the step index and pose it was captured with. In lockstep mode, acknowledge the master only after the readback for that step completes.

For offline dataset generation where real time does not matter, the Movie Render Graph (production-ready in UE 5.8) gives higher image quality, including the path tracer, at the cost of speed.

#Depth

Set CaptureSource = SCS_SceneDepth with a float target (RTF_R32f). The value is z-depth along the optical axis in cm, not radial range. Convert per pixel: r = z · sqrt(1 + ((u − cx) / fx)² + ((v − cy) / fy)²). Never store depth in 16-bit float; the quantization at range is severe.

#Segmentation

  1. Project Settings → Rendering → Custom Depth-Stencil Pass → Enabled with Stencil.

  2. On each primitive: SetRenderCustomDepth(true) and SetCustomDepthStencilValue(ClassId) (0–255).

  3. A post-process material reads SceneTexture:CustomStencil and writes the class ID as an exact color. Add it to the capture's PostProcessSettings.WeightedBlendables.

  4. Make sure nothing alters the IDs after your material: no tone mapping on that output, no anti-aliasing, an 8-bit linear target, nearest sampling. Verify that edge pixels contain only valid IDs.

The stencil gives 255 classes. Instance IDs need more bits; encode them through Custom Primitive Data on each component and an override material.

#Lidar

Option A: ray casting. Precompute beam directions, then trace in parallel against complex collision after physics has finished:

void USimLidarComponent::FireSlice(int32 FirstBeam, int32 NumBeams, TArray<FSimLidarReturn>& Out)
{
    const FTransform Pose = GetComponentTransform();
    Out.SetNum(NumBeams);

    FCollisionQueryParams Params(SCENE_QUERY_STAT(SimLidar), /*bTraceComplex=*/true);
    Params.AddIgnoredActor(GetOwner());
    Params.bReturnPhysicalMaterial = true;

    ParallelFor(NumBeams, [&](int32 i)
    {
        const FVector DirLocal = BeamDirections[FirstBeam + i];
        const FVector Start    = Pose.GetLocation();
        const FVector End      = Start + Pose.TransformVectorNoScale(DirLocal) * MaxRangeCm;

        FHitResult Hit;
        if (GetWorld()->LineTraceSingleByChannel(Hit, Start, End, ECC_GameTraceChannel2, Params))
            Out[i] = { Hit.Distance, DirLocal, ReflectivityOf(Hit.PhysMaterial.Get()) };
        else
            Out[i] = FSimLidarReturn::NoReturn();
    });

    // Apply range noise afterwards, in index order, from a seeded stream: keeps results reproducible
}

Run this in TG_PostPhysics, when the physics scene is not being written. CARLA's ray-cast lidar parallelizes traces the same way; read its source to see how it guards scene access in its engine version.

Model the spin. A 10 Hz spinning lidar does not capture a whole revolution instantaneously. With a 1 kHz simulation step, fire the 3.6° azimuth slice for each step from that step's pose. Motion distortion then falls out naturally, exactly as on the real sensor.

Option B: depth-buffer lidar. Render depth from several captures covering the field of view and sample them per beam on the GPU. It scales to very high point counts and sees exactly the rendered geometry, but it aliases at range, cannot do multiple returns easily, and adds readback.

What rays hit matters as much as how they are cast. Foliage often has no collision. Nanite meshes use a lower-resolution fallback mesh for collision, so complex traces may not match rendered detail. Audit collision on every asset class your lidar will see.

#Radar

A practical ray-based radar casts a pattern of traces or sweeps across the beam, and for each hit computes range, azimuth, elevation and radial velocity (target velocity from your entity registry, not from rendering), plus a cross-section from the physical material or an entity table. Bin hits into resolution cells, apply detection probability and false alarms, and add noise. This ignores multipath and diffraction. For higher fidelity, export geometry from Unreal into a dedicated electromagnetic model.

#IMU, GNSS, barometer and magnetometer

Compute these from SimMath truth, never by differentiating rendered transforms.

  • IMU: specific force f_b = R_bn (a_n − g_n) and body rates ω_b, plus bias, Gauss-Markov bias instability, angle and velocity random walk, scale factor, misalignment, quantization, and the sensor's own sample rate and anti-alias filter. Sample on the simulation clock (for example every 2.5 ms for 400 Hz), independent of frames.

  • GNSS: truth position to geodetic through your WGS84 code or the georeference, then correlated error, white noise, latency, update rate and dropouts. Unreal geometry adds something useful here: trace from the antenna toward satellite directions to model urban-canyon masking.

  • Barometer and magnetometer: standard atmosphere and magnetic-field models in SimMath.

#Validate every sensor

  • Camera: render a checkerboard in-engine, calibrate with OpenCV, and compare the recovered intrinsics with your formula.

  • Depth and lidar: scenes with planes and spheres at known distances; compare against analytic ranges and characterize the error.

  • IMU: run an hour of static simulated data and compute the Allan deviation; random walk and bias instability must match your configuration.

  • Timing: log trigger step, capture frame and readback frame; the latency must be constant.

#Chapter 9 — Interfacing with the outside world

Treat the Unreal process as one node in a larger system and connect it through a narrow, versioned interface. Keep heavy middleware (ROS 2, DDS, DIS, HLA) in a sidecar process where you can, so its build quirks never enter the engine build and either side can restart independently.

#Split the control plane from the data plane

  • Control plane: request/response commands such as load scenario, spawn entity, set parameter, step, reset. Low bandwidth, must be reliable. RPC over TCP fits.

  • Data plane: sensor streams. High bandwidth, tolerant of a dropped frame in interactive use but not in batch. Shared memory on one machine, TCP or UDP streams across machines.

Every message on both planes carries the step index and simulation time. That one rule makes logging, replay and debugging tractable.

#Sockets inside Unreal

Add Sockets and Networking to your Build.cs. Receive on a worker thread and hand messages to the game thread through a lock-free queue; apply them at step boundaries.

FSocket* Socket = FUdpSocketBuilder(TEXT("SimCmd"))
    .AsNonBlocking()
    .AsReusable()
    .BoundToEndpoint(FIPv4Endpoint(FIPv4Address::Any, 47000))
    .WithReceiveBufferSize(1 << 20);

class FSimCmdReceiver final : public FRunnable
{
public:
    explicit FSimCmdReceiver(FSocket* InSocket) : Socket(InSocket) {}

    virtual uint32 Run() override
    {
        TArray<uint8> Buffer;
        Buffer.SetNumUninitialized(65536);
        TSharedRef<FInternetAddr> From = ISocketSubsystem::Get(PLATFORM_SOCKETSUBSYSTEM)->CreateInternetAddr();

        while (!bStop)
        {
            int32 BytesRead = 0;
            if (Socket->Wait(ESocketWaitConditions::WaitForRead, FTimespan::FromMilliseconds(50)) &&
                Socket->RecvFrom(Buffer.GetData(), Buffer.Num(), BytesRead, *From))
            {
                FSimCommand Cmd;
                if (DecodeCommand(Buffer.GetData(), BytesRead, Cmd))   // checks version + length
                {
                    Inbox.Enqueue(MoveTemp(Cmd));
                }
            }
        }
        return 0;
    }

    virtual void Stop() override { bStop = true; }

    TQueue<FSimCommand, EQueueMode::Spsc> Inbox;   // game thread drains this at step start

private:
    FSocket* Socket;
    std::atomic<bool> bStop{ false };
};

// Stop:   Receiver->Stop(); Thread->WaitForCompletion();

Commands that should take effect at a specific step carry that target step. The game thread applies them when the clock reaches it, which keeps command timing reproducible regardless of network jitter.

#Shared memory for sensor data

FPlatformMemory::MapNamedSharedMemoryRegion creates or opens a named shared region on Windows and Linux. Lay it out as a ring of fixed-size slots, each with a header (sequence number, step index, sim time, width, height, pixel format, pose) followed by the payload. Use a sequence counter written before and after the payload, or double buffering, so the reader never sees a torn frame. A Python reader built on mmap is a great debugging tool.

#ROS 2

The sidecar pattern works well here: a small rclcpp node reads shared memory and UDP, publishes sensor_msgs/Image, PointCloud2, Imu, NavSatFix and TF, and forwards command topics back to the simulation.

  • Frames. ROS convention (REP 103) is x forward, y left, z up for bodies and ENU for the world. From Unreal body axes that is FLU = (X, −Y, Z) / 100. Add it to your frames module next to NED.

  • Time. Publish your simulation time on /clock and run ROS nodes with use_sim_time. Without it, lockstep and faster-than-real-time runs break every ROS node that uses timers.

  • In-process alternatives. rclUE embeds ROS 2 in Unreal, but its documented main support lags current engine versions, so check before committing. CARLA 0.10 added a native in-process ROS 2 interface, a good example of what a large team can maintain.

#DIS and HLA

  • DIS (IEEE 1278.1) sends Entity State PDUs over UDP with positions in ECEF and orientations as Euler angles in an Earth-referenced frame. Do those conversions in SimMath, tested against known PDUs.

  • Open-DIS is an open-source DIS implementation (C++, Java, Python and more) from the Naval Postgraduate School's MOVES Institute.

  • GRILL DIS for Unreal is AFRL's open-source plugin built on Open-DIS and Epic's Georeferencing plugin. Its marketplace listing covers UE 4.27 and 5.0–5.3, so expect to port it, but its architecture (socket, PDU processing and entity management as swappable components) is worth studying.

  • HLA needs an RTI. Keep the RTI and FOM handling in a sidecar federate and feed Unreal through your own interface.

  • Remote entities arrive at network rates, not frame rates. Apply DIS-style dead reckoning in SimMath and render the extrapolated state.

#Chapter 10 — Building worlds

You need enough world-building skill to create environments whose geometry, materials and collision you trust, not a game artist's skill set. That means terrain, georeferenced tiles, procedural placement, and knowing what each rendering feature does to your sensors.

#Two kinds of world

  • Synthetic and local: Landscape terrain, placed meshes and procedural scatter. Best for controlled tests where you know every surface.

  • Geospatial: Cesium for Unreal streams 3D Tiles (global terrain, photogrammetry, building footprints) from Cesium ion or your own tile server. Esri's ArcGIS Maps SDK for Unreal is an alternative; its 2.4 release supports UE 5.6–5.8. Your own elevation and imagery can be converted to 3D Tiles or imported as a Landscape.

Check data licenses before generating datasets from third-party tiles; terms for derived data vary by provider.

#Landscape terrain

  • Heightmaps import as 16-bit grayscale PNG or RAW. With the default Z scale of 100, the 65,536 height steps span 512 m (−256 m to +256 m) at 0.78 cm per step. Scale Z to fit your real elevation range and record the mapping.

  • Landscape collision can use a coarser mip than rendering (Collision Mip Level and Simple Collision Mip Level). Lidar and ground contact hit collision, so set these deliberately.

  • UE 5.8 adds an experimental Mesh Terrain system for terrain shapes a heightmap cannot represent, such as overhangs and caves.

#World Partition and streaming

Large worlds are split into grid cells that stream in around streaming sources, which by default means the player. A simulation has a problem a game does not: a sensor on a vehicle 20 km from the viewer sees unloaded cells.

  • Add a UWorldPartitionStreamingSourceComponent to each vehicle that carries sensors.

  • Before the first capture at a new location, wait until cell streaming, texture streaming and Nanite streaming have settled. In lockstep mode, the clock simply does not advance until they have.

  • Distant geometry renders as HLOD proxies, which usually have no collision. A long-range lidar or altimeter can pass straight through them. Decide what long-range sensors should hit and test it.

  • Enable One File Per Actor so several people can edit a level under source control without lock conflicts.

#Procedural content generation

The PCG framework, production-ready since UE 5.7, builds scatter (vegetation, rocks, clutter, buildings) from graphs. Graphs take seeds, which makes them ideal for reproducible scene variation: the same seed must give the same scene, and different seeds give the randomized environments you need for robustness testing and synthetic training data.

#Materials, from a sensor engineer's view

  • Unreal materials are physically based for visible light: base color, metallic, roughness, normal, emissive. Substrate, production-ready in 5.7, adds layered materials.

  • Materials carry no infrared or radio-frequency properties. Attach those through physical materials (surface type) and a data table mapping surface type to emissivity, lidar reflectivity, radar cross-section and so on.

  • Material Parameter Collections set global values every material can read, for example switching the whole scene to a thermal rendering mode.

  • Post-process materials implement sensor effects: noise, distortion, thermal palettes, segmentation output.

#Chapter 11 — Performance, threading and scale

Measure before optimizing. Unreal Insights shows which thread bounds a frame, and simulation workloads usually end up GPU-bound by sensor captures or game-thread-bound by per-entity overhead. Both have standard fixes.

#The threads that matter

  • Game thread: ticks, gameplay code, your adapter layer, and all UObject access.

  • Render thread: turns scene state into render commands; runs about one frame behind.

  • RHI thread: submits those commands to the graphics API.

  • Physics: Chaos runs on worker tasks, or on its own thread with async physics.

  • Task graph workers: ParallelFor, UE::Tasks, async jobs.

Because these run as a pipeline, frame time is roughly the slowest of game thread, render thread and GPU, not their sum.

#Measuring

  • stat unit shows Frame, Game, Draw (render thread), RHIT and GPU times in milliseconds. Start here every time.

  • stat gpu and ProfileGPU break down GPU passes, which is where scene captures show up.

  • Unreal Insights is the real profiler. Launch with -trace=default,gpu (add memory when needed), then open the .utrace file in UnrealInsights. It shows per-thread timelines, GPU scopes, bookmarks and memory.

  • Instrument your own code so it appears in Insights:

void USimClockSubsystem::AdvanceFrame(double FrameDt)
{
    TRACE_CPUPROFILER_EVENT_SCOPE(Sim_AdvanceFrame);
    // ...
    {
        TRACE_CPUPROFILER_EVENT_SCOPE(Sim_CoreStep);
        Core->Step(StepDt);

    TRACE_BOOKMARK(TEXT("SimStep %lld"), StepIndex);
}

Take real numbers from standalone or packaged Development/Test builds. PIE timings include the editor.

The rules: UObjects, Actors and components belong to the game thread. Render resources belong to the render thread. Code inside async physics callbacks uses physics-thread APIs. Breaking these rules produces crashes that appear far from their cause.

#A high-rate simulation worker

When dynamics run at 1–10 kHz, put SimMath on its own FRunnable thread, decoupled from frames. The worker writes state snapshots into a triple buffer; at frame start the game thread takes the latest complete snapshot and pushes it to Actors. In lockstep mode the game thread instead signals "advance k steps" and waits, which can overlap with the render thread still drawing the previous frame. Because SimMath has no Unreal types, it is easy to run under a thread sanitizer in your standalone build.

#Per-entity cost on the game thread

Actors are heavyweight: each one ticks, propagates transforms through its component tree, runs overlap tests and updates render proxies. Thousands of moving Actors will dominate the game thread. Fixes, in order of effort:

  1. Turn off ticking on Actors that do not need it; let one manager update many.

  2. Turn off collision and overlap events on purely visual entities.

  3. Keep component trees shallow for entities that exist in large numbers.

  4. Render many identical objects through one Instanced Static Mesh component and update instance transforms in batches from a SimMath array.

  5. Lower update rates for distant or off-screen entities.

#Mass Entity

Mass is Unreal's data-oriented entity-component system: entities are IDs, fragments are data, and processors run over chunks of entities in parallel. It powers crowds and traffic in Epic's samples, and UE 5.8 uses it to orchestrate MetaHuman crowds. It suits thousands of simple agents such as traffic, pedestrians or swarms. The learning curve is steep and documentation is thin, so study a sample project first. For many simulations, keeping agents in your own arrays and rendering them through instanced meshes achieves the same result with less machinery.

#GPU budget for sensors

  • Every scene capture is a full scene render, so N cameras cost roughly N times the GPU time. Trim each capture: lower resolution, show flags that drop shadows, fog or global illumination when a depth or segmentation pass doesn't need them, and "show only" lists of relevant primitives.

  • Capture at the sensor rate, not the frame rate.

  • One 1920 × 1080 RGBA8 frame is 8.3 MB; 30 Hz is about 250 MB/s per camera. PCIe handles that easily; CPU copies and image encoding often do not. Encode on worker threads or write raw buffers.

  • For batch throughput, run several simulation instances, one per GPU (-graphicsadapter=N), rather than trying to spread one instance across GPUs.

#Memory and loading

  • Load every asset a scenario needs before the clock starts (async load through FStreamableManager, then wait). Mid-run loads cause hitches and timing changes.

  • Size the texture streaming pool (r.Streaming.PoolSize) for your sensor resolutions.

  • Avoid creating and destroying UObjects in the loop; garbage-collection spikes are frame spikes.

#Functional tests

A functional test is an Actor you place in a test map. It starts when the map loads, drives the scenario, and calls FinishTest(EFunctionalTestResult::Succeeded, ...) or Failed. Typical use: load a scenario, run 10 s of simulation in lockstep, assert the vehicle ended within tolerance of a golden position. They appear in the automation tree under the map's name, so the same command line runs them.

#Commandlets

A commandlet is a headless editor program: subclass UCommandlet, implement Main, and run it with UnrealEditor-Cmd.exe MySim.uproject -run=SimValidate. Use commandlets to validate every vehicle config, bake lookup tables, convert data, or generate scenario variants in CI. Keep them in an editor-only module.

#Batch and Monte Carlo runs

The design that scales:

  1. A run manifest per run (JSON or YAML): engine and project commit IDs, scenario, run seed, parameter overrides, sensor configuration, output directory.

  2. A launcher script (Python) that samples parameters, writes manifests, launches packaged instances (MySim.exe -Manifest=run_0042.json -Lockstep -RenderOffscreen -unattended -log), keeps N running per GPU, enforces timeouts and retries crashes.

  3. Simulation outputs per run: trajectories and events (Parquet, HDF5 or binary), sensor data, and a summary JSON with metrics and exit status. End the process with FPlatformMisc::RequestExitWithStatus(false, ExitCode) so the launcher can tell success from failure.

  4. Seeds: derive every per-entity and per-sensor seed from the run seed with a hash, and log them.

  5. Analysis in pandas: dispersions, sensitivities, failure clustering.

The acceptance test for the whole pipeline: any run can be reproduced exactly from its manifest and build ID.

#Regression in CI

  • Keep golden runs. Compare trajectories channel by channel with absolute and relative tolerances. Use bit-exact hashes only within one machine and build.

  • A typical pipeline: build → SimMath unit tests → automation tests with -nullrhi → short lockstep scenarios on a GPU runner → compare against goldens → publish a report.

  • Epic's BuildGraph scripts describe build steps in XML and run on any CI system; Epic's own Horde system is an option at larger scale. A shared derived-data cache makes CI cooks much faster.

#CARLA

CARLA 0.10.0 moved from UE 4.26 to UE 5.5, switched physics from PhysX to Chaos, rebuilt its build system on CMake, reworked its segmentation sensors and added a native in-process ROS 2 interface. The UE4 line continues separately, and the UE5 documentation lives at carla-ue5.readthedocs.io. At release, 0.10.0 listed real gaps, including fixed daylight weather, no large-map or OpenDRIVE import support, and a recommended 16 GB of GPU memory; check current release notes before building on it.

What to study, with a question for each:

  • Architecture. An Unreal server running CARLA's plugin talks to C++ and Python clients over msgpack-RPC for commands, with separate streams for sensor data. Why split commands from sensor data?

  • Synchronous mode. The client sets a fixed delta and calls world.tick(); the server advances exactly one frame and stamps every sensor output with the frame number. Find where the server hooks the world tick and fixes the engine's delta. How does it keep sensors from running ahead of the client?

  • Sensors. Cameras use scene captures and post-process materials; the ray-cast lidar traces in parallel; IMU and GNSS come from actor state plus noise. How do they schedule each sensor relative to the frame, and how do they handle readback?

  • Supporting systems. The traffic manager, OpenDRIVE road networks, ScenarioRunner and the Leaderboard show what a full test ecosystem around a simulator looks like.

#AirSim and Colosseum

Microsoft archived AirSim and announced Project AirSim as its successor. Colosseum is a community fork that moved the codebase to UE5.

The design lesson is the important part: AirSim ships its own lightweight physics engine for vehicles and uses Unreal for rendering and collision. That is the embedded-core pattern from Chapter 1, proven in a widely used tool. Study:

  • how the vehicle physics engine is stepped and how its state reaches Actors;

  • the clock-control API (pause, continue for a duration, clock speed);

  • the image-request API, which captures multiple camera types per request;

  • how settings are loaded from a JSON file instead of being authored in levels.

The codebase predates many UE5 features and has rough edges. Read it for patterns, not as a dependency to build on.

#MathWorks Simulation 3D

MathWorks' automated-driving and UAV toolboxes include Simulink blocks that co-simulate with an Unreal-based 3D environment, with Simulink owning time. If your organization uses Simulink, this is the closest commercial example of Pattern B, and its documentation on timing and sample rates is a useful statement of the contract a lockstep renderer must honor.

#GRILL DIS for Unreal

Covered in Chapter 9. Read it for how it decouples sockets, PDU processing and entity management, and how it uses Epic's Georeferencing plugin for Earth-referenced conversions.

#Epic's samples

City Sample demonstrates World Partition at city scale and Mass-driven traffic and crowds. Content Examples demonstrates individual engine features one room at a time, which is the quickest way to see what a rendering or physics feature does before reading its code.

#How to read a large Unreal codebase

  1. Start from the entry point you care about (for example the function that handles a synchronous tick request) and follow calls, not files.

  2. Keep a sequence diagram in your notebook as you go.

  3. Use your IDE's find-references heavily; reflection macros hide some call paths, so also search for function names as strings.

  4. Build and run the project with a debugger attached, set a breakpoint at the entry point, and step.

#Milestones and acceptance criteria

  1. Skeleton. Plugin with SimMath, SimRuntime, SimSensors and SimBridge modules; SimMath also builds under CMake with GoogleTest; minimal game mode and an empty test level. Accept: clean build with unity off; all unit tests green.

  2. Clock. Both timing patterns, an integer step counter, and a determinism test. Accept: the state hash at t = 30 s is identical at 30 fps, 60 fps and uncapped; N lockstep commands advance exactly N frames.

  3. Vehicle. 6DOF model, kinematic drive, frames module with the Chapter 6 tests. Accept: energy is conserved to integrator tolerance with drag off; every frame test passes; rendered attitude matches commanded attitude.

  4. World. Georeferenced terrain, a streaming source on the vehicle, sun position. Accept: a vehicle placed by latitude, longitude and height lands within 0.1 m of an independent GeographicLib computation.

  5. Navigation sensors. IMU, GNSS and barometer on the simulation clock. Accept: Allan deviation of simulated IMU output matches the configured noise; GNSS error statistics match the configured model.

  6. Cameras. EO, depth and segmentation with asynchronous readback and per-frame metadata. Accept: OpenCV calibration recovers intrinsics within 0.5 px; every segmentation pixel holds a valid ID; capture-to-readback latency is constant.

  7. Lidar. Sliced spinning lidar with noise. Accept: plane-target errors match the noise model; motion distortion is visible and correct at 15 m/s.

  8. Interfaces. RPC, shared memory and the ROS 2 sidecar with /clock. Accept: RViz shows every sensor in the correct frame; a Python script drives a full scenario with -RenderOffscreen.

  9. Closed loop. The external controller flies a waypoint mission from sensor data alone. Accept: a landing-error tolerance you set in advance, met on the nominal run.

  10. Batch and regression. Manifests, launcher, Monte Carlo over wind and sensor-noise dispersions, golden-run comparison in CI. Accept: any run reproduces exactly from its manifest and build ID; a dispersion plot; CI fails when a change moves a golden trajectory outside tolerance.

  1. Using frame delta as the simulation dt.

  2. Using TickInterval as a sensor rate.

  3. Holding a UObject pointer without UPROPERTY or FGCObject.
