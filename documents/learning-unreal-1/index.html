Learning Unreal, Part 1: How Unreal Engine Works

25 min read

#1. What Unreal Engine is

Unreal Engine (UE) is Epic Games' real-time 3D engine: a large C++ framework for simulation, rendering, physics, audio and input, plus an editor for building worlds. It started as a game engine and now also drives film virtual production, training simulators, digital twins and synthetic sensor data for autonomy. The full engine source is on GitHub once you link your Epic account to GitHub.

In your terms, UE is a variable-step simulation loop over a world of objects, with a film-grade renderer attached. You extend it with a C++ module (a DLL) that the engine loads, written in a reflected dialect of C++ that adds garbage collection and editor integration. The editor is the same engine running with authoring tools on top.

Aerospace postings that ask for Unreal usually mean C++ work on simulator visuals, synthetic environments, or sensor and autonomy testbeds; a later section covers what that looks like. Part 2 applies everything here to the Lake Highland Stray project on your machine.

#2. The big picture: engine, editor, project, game

Unreal splits your disk into the engine, installed once and shared, and your project, a folder that names the engine version it needs. The editor is the engine plus authoring tools; the packaged game is the engine plus your code and cooked content, minus the tools.

The same source and assets feed both paths: the editor loads them live while you develop, and packaging compiles and cooks them into a standalone game.

PieceWhat it isIn this project
EngineHundreds of C++ modules (Core, Engine, Renderer, physics, audio) prebuilt as DLLs, plus build toolsC:\Program Files\Epic Games\UE_5.8

Config.ini files: default map, renderer settings, input, packagingConfig\Default*.ini
Packaged gameA standalone .exe plus compressed, platform-specific ("cooked") contentBuild\Package\Windows\LakeHighlandStray.exe

Assets are serialized objects, not source files. A .uasset file is a binary snapshot of one or more engine objects (a mesh, a material, a Blueprint class) plus references to other assets. You edit them in the editor or with editor scripts, and refer to them by path: /Game/Maps/LakeHighland means Content\Maps\LakeHighland.umap.

The editor is a live instance of your game. Press Play and the editor runs the game in-process on a copy of the level (Play In Editor, or PIE). You can pause, detach the camera, inspect any object and change properties while it runs; stopping PIE discards the copy.

Authoring and simulating are two states of the same objects. In the editor, an object's property values are saved into the level file; when play starts, the engine calls BeginPlay on it and starts ticking it. Code inside #if WITH_EDITOR blocks exists only in editor builds and is compiled out of the shipped game.

Packaging is build, cook, stage, pak. The game target is compiled without editor code, every referenced asset is cooked into the platform's runtime format (compressed textures, compiled shaders, editor-only data stripped), and the result is bundled into container files beside the .exe. The Unreal Automation Tool runs all of it (RunUAT.bat BuildCookRun); this project wraps that in Pipeline\ue\package.ps1.

#3. The world model: World, Level, Actor, Component

Everything that exists during play lives in a World, which holds Levels; levels hold Actors, and actors are assembled from Components. It is a scene graph whose nodes are full C++ objects with behavior, not just data records.

The cat's capsule is its root component: the mesh, the camera boom and the sounds hang off it with relative transforms, while the movement component has no transform at all.

ConceptClassWhat it isExample in this project
WorldUWorldThe running simulation: its levels, actors, physics scene and timers. The editor, each Play-In-Editor session and the packaged game each get their ownThe world created when the LakeHighland map loads
LevelULevel, saved as .umapA saved collection of actors. Big worlds stream parts in and out (World Partition)/Game/Maps/LakeHighland
ActorAActorAnything placed in or spawned into a level. Has a transform, can tick, can be spawned and destroyedAFeedingStation, AStrayCat, ALHDayNight

Primitive componentUPrimitiveComponentA scene component with geometry, so it can render, collide or bothUStaticMeshComponent for each bowl, UCapsuleComponent for the cat's collision

An actor's transform is its root component's transform. Every other scene component attaches to the root, or to another component, with a relative transform, and the chain composes like any scene graph. AFeedingStation is an empty root USceneComponent with six static-mesh components attached: bowl, kibble, scatter, plate, wet food and water bowl.

Actors are things; components are capabilities. Make a class an actor when it exists on its own in the world (a cat, a lamp, a manager), and a component when it is a capability several actors share (a mesh, a light, a movement model, a sound). Unlike a pure entity-component system, components carry their own logic and actors are ordinary C++ classes with virtual functions; Unreal's data-oriented ECS, called Mass, exists for crowds and traffic.

You create, find and destroy actors through the world. GetWorld()->SpawnActor<AFeedingStation>(Location, Rotation) creates one at run time, Destroy() removes it, and TActorIterator<AStrayCat> walks every actor of a type. This project spawns its strays, the man, the bowls and the day-night system from C++ in ALHGameMode at startup, while a Python build script places the static scenery into the level.

#4. UObject: Unreal's C++ dialect

Most Unreal classes derive from UObject, which layers reflection, garbage collection, serialization and editor exposure on top of ordinary C++. You opt in with macros, and a code generator reads them before the compiler runs. Here is a trimmed header from this project:

#include "FeedingStation.generated.h"   // must be the last include

UCLASS()                                 // register the class with the reflection system
class LAKEHIGHLANDSTRAY_API AFeedingStation : public AActor
{
    GENERATED_BODY()                     // UHT pastes generated boilerplate here
public:
    AFeedingStation();                   // creates components, sets defaults

    UPROPERTY(VisibleAnywhere)           // GC-tracked, shown in the editor's Details panel
    TObjectPtr<UStaticMeshComponent> Bowl;

    UPROPERTY(VisibleAnywhere, BlueprintReadOnly)
    float DryAmount = 0.f;               // 0..1 portions in the bowl

    void Refill(EFoodKind Kind);         // plain C++: invisible to Blueprints and the editor
};

Reflection is code generation. Before each compile, the Unreal Header Tool (UHT) scans headers for UCLASS, USTRUCT, UENUM, UPROPERTY and UFUNCTION and writes a .generated.h file of type metadata, much like Qt's moc. That metadata lets the editor show and save your properties, lets Blueprints call your functions, and lets the garbage collector find references.

Garbage collection replaces delete. You create UObjects with NewObject<T>(), CreateDefaultSubobject<T>() or SpawnActor<T>() and never delete them; a periodic mark-and-sweep collector frees whatever is unreachable through UPROPERTY references. The classic bug is a raw UObject* member without UPROPERTY(): the collector cannot see it and may free the object under you, which is why Wildlife.h holds its meshes in UPROPERTY() members.

Every class has a Class Default Object (CDO). At startup the engine constructs one instance of each class as the template that later instances copy. So constructors run early, in the editor too, and must only create components and set defaults; anything that touches the world or other actors belongs in BeginPlay.

Assets are referenced by path. ConstructorHelpers::FObjectFinder<USoundBase>(TEXT("/Game/LH/Audio/S_KibblePour.S_KibblePour")) in FeedingStation.cpp is a hard reference: the sound loads whenever the class does. TSoftObjectPtr is the deferred alternative for assets you load on demand.

Casting and errors work differently. Cast<APlayerCat>(Pawn) is the reflection-based dynamic_cast and returns null on a mismatch. Unreal code does not use C++ exceptions; it reports problems with return values, logs and assertions (check, ensure).

#5. The Gameplay Framework: who is in charge

Unreal ships a standard cast of classes for "a player controls something in a world under some rules", and the engine creates and connects them for you. You subclass the ones you need and name your subclasses in config or in your GameMode.

Input reaches the cat only through its controller; the strays share the cat's base class but are driven by AI controllers, and the man skips a controller entirely.

Possession separates the brain from the body. A controller possesses a pawn: input or AI drives the controller, and the controller drives the pawn. Swap the pawn and the same controller flies a drone instead of walking a cat; swap the controller and the same cat is driven by AI.

The startup order is fixed. The engine creates the GameInstance and its subsystems, loads the default map, and spawns the GameMode. For each player it then spawns a PlayerController and HUD, spawns the default pawn and possesses it, and only after that calls BeginPlay across the world.

This project's Config/DefaultEngine.ini names LHGameMode as the default game mode and LHGameInstance as the game instance. The GameMode's constructor names the rest of the cast:

ALHGameMode::ALHGameMode()
{
    DefaultPawnClass      = APlayerCat::StaticClass();           // spawned for the player and possessed
    PlayerControllerClass = ALHPlayerController::StaticClass();
    HUDClass              = ALHHUD::StaticClass();
}

The GameMode exists only on the server. In multiplayer, clients never get a GameMode; GameState and PlayerState replicate to them instead. A single-player game is its own server, so this project uses the GameMode as a global hub: the cat, the man and the HUD all reach it through GetWorld()->GetAuthGameMode(), which would not work on a client.

#6. Time: the frame loop, Tick and the object lifecycle

Unreal advances the world once per rendered frame by a measured, variable time step, DeltaSeconds. There is no fixed simulation rate unless you ask for one, and that is the biggest mental shift from a fixed-step simulator.

One frame on the game thread, simplified:

  1. Pump operating-system messages; key, mouse and gamepad events are queued for the player controller.

  2. Tick actors and components in tick groups: TG_PrePhysics (the player controller turns queued input into actions; character movement runs), then the physics step (TG_StartPhysics to TG_EndPhysics, with TG_DuringPhysics work overlapping it), then TG_PostPhysics. An actor picks its group and can declare prerequisite actors.

  3. Fire timers set with GetWorldTimerManager().SetTimer(...), update cameras, then run the last tick groups (TG_PostUpdateWork).

  4. Hand the scene to the render thread and start the next frame.

The render thread draws frame N while the game thread computes frame N+1, and the RHI thread feeds the GPU behind it, so the image trails the simulation by one to two frames. Animation, physics and particles fan out to worker threads through a task graph. This project's UBlendAnimInstance follows the rule for that: it computes blend weights on the game thread, copies them into a proxy in PreUpdate, and the proxy's Evaluate builds the pose where a worker thread can run it.

Most of your C++ runs in the highlighted TG_PrePhysics step; frame N then moves to the render thread and the GPU while the game thread starts on the next frames.

Tick is your time-step function. virtual void Tick(float DeltaSeconds) runs once per frame on any actor or component that enables it (PrimaryActorTick.bCanEverTick = true in the constructor). ALHDayNight::Tick is a one-line integrator, TimeOfDay += DeltaSeconds * TimeScale * NapMultiplier / 3600.f, and with TimeScale = 60 one game hour passes per real minute.

Variable steps have consequences you already know. Results depend on frame rate, a 200 ms hitch can tunnel through geometry or destabilize stiff dynamics, and runs are not reproducible. Unreal's helpers are DeltaTime-aware but approximate: FMath::FInterpTo takes one explicit-Euler step of first-order lag, x += (target − x) × clamp(k × dt, 0, 1), not the exact 1 − e^(−k × dt) blend.

Options for fixed-step work:

  • Inside your own Tick: clamp, substep, or run a fixed-step accumulator ("fix your timestep") and interpolate what you render.

  • Physics: Chaos rigid bodies can substep, or run asynchronously at a fixed step on their own thread (Project Settings > Physics).

  • Engine-wide: Project Settings > General Settings > Framerate > Use Fixed Frame Rate gives every frame the same DeltaSeconds, for deterministic captures and repeatable tests.

  • Outside the engine: a high-rate flight model usually runs on its own thread or process, and Unreal renders its latest state each frame.

Game time and real time differ. Pausing and time dilation scale the DeltaSeconds actors receive, and CustomTimeDilation does it per actor. ALHGameMode::Tick drives fades and on-screen messages from FApp::GetDeltaTime(), the engine's raw frame time, rather than the world's scaled delta.

Discrete events need crossing detection. In a variable-step loop, "at t = 2.0 s" means the first frame whose interval contains 2.0 s. The project's automated test uses exactly that: Crossed(T) is true when StepTimer >= T && StepTimer - DeltaSeconds < T, which stays correct through long frames.

#7. Space: coordinates, units and rotations

Unreal's world frame is left-handed and Z-up: +X forward, +Y right, +Z up, and one Unreal unit is one centimeter. Positions are double precision, FRotator angles are degrees, and transform composition reads left to right.

QuantityUnrealTypical aerospace
HandednessLeft-handedRight-handed
AxesX forward, Y right, Z upNED (x north, y east, z down) or ENU (x east, y north, z up)
LengthCentimeters (1 uu = 1 cm)Meters or feet
Mass, time, gravitykg, s, gravity −980 cm/s²kg, s, 9.81 m/s²
AnglesDegrees in FRotator and most APIs; radians in FMath::Sin and FQuat axis-angleRadians in code
AttitudeFRotator(Pitch, Yaw, Roll), FQuat3-2-1 Euler angles (heading, pitch, bank), quaternions, DCMs
PrecisionDoubles: FVector is TVector<double> since UE 5.0 ("Large World Coordinates"); FVector3f is the float versionDoubles

From NED, flip one axis and scale. Map (north, east, down) in meters to (X, Y, Z) = (100 × N, 100 × E, −100 × D). With that mapping, FRotator(θ, ψ, φ) reproduces the aerospace 3-2-1 attitude exactly (heading ψ, pitch θ, bank φ) with the same signs: positive yaw turns right, positive pitch raises the nose, positive roll drops the right wing.

From ENU, flip Y. Keep X east and Z up, and Y must point south to stay left-handed. This project does exactly that in LHTypes.h, because its map data comes in local east-north-up meters:

/** Local map frame (metres, x = east, y = north) <-> Unreal (cm, X = east, Y = south). */
inline FVector ToUE(double X, double Y, double Z) { return FVector(X * 100.0, -Y * 100.0, Z * 100.0); }

Watch argument order and multiplication order. The constructor is FRotator(Pitch, Yaw, Roll), not yaw first. FTransform composes left to right (ChildWorld = ChildRelative * ParentWorld), while FQuat composes like standard math (A * B applies B first, then A).

Large worlds work. Since UE 5.0, positions are doubles on the CPU and the GPU renders relative to the camera, so planet-scale scenes such as a WGS84 globe from Cesium for Unreal render without the jitter 32-bit floats used to cause.

#8. Blueprints and C++

Blueprints are Unreal's visual scripting language: node graphs, saved as assets, that compile to bytecode for a virtual machine inside the engine. A Blueprint class subclasses a C++ class (or another Blueprint), adds components, overrides events and sets default values, all in the editor.

Widget BlueprintUMG user interface: menus, HUD elements

C++ decides what Blueprints can touch:

UPROPERTY(BlueprintReadWrite), BlueprintReadOnlyReading or setting the variable in graphs

The usual division of labor: systems, math and anything performance-critical in C++; asset choices, tuning and level-specific scripting in Blueprints. A typical character is a C++ class that holds the logic plus a thin Blueprint subclass that picks the mesh, animation and sounds, so artists can change them without recompiling.

Blueprints have costs. Graphs run slower than native code, they are binary assets that do not diff or merge in source control, and large graphs get hard to follow. Teams usually set rules on how much logic may live in them.

This project has no Blueprints of its own. Every class is C++, assets are found by path in constructors, an AnimInstance written in C++ replaces the Animation Blueprint, and a canvas-drawn HUD replaces UMG. That reads well top to bottom for a C++ developer, but changing a mesh or a sound means recompiling; Part 2 suggests where Blueprint subclasses would help.

#9. Content and rendering

The renderer turns meshes, materials and lights into pixels every frame, and most of what you see is decided by assets and settings rather than code. Asset names follow prefix conventions, so a name tells you the type.

Materials are shaders authored as graphs. Each material compiles to HLSL for every platform and mesh type that uses it, which is why a first launch spends minutes compiling shaders. Material instances reuse the compiled shader and only change parameters, so they are the cheap way to make variations; this project's ue_materials.py even builds its graphs from Python with hand-written HLSL in Custom nodes.

Unreal 5 renderer features you will hear about:

  • Nanite: virtualized geometry that streams and culls clusters of triangles, so very dense meshes render cheaply. Here small instanced meshes (trees, shrubs, cars) use it, while large merged tiles were imported without it after they rendered coarse.

  • Lumen: dynamic global illumination and reflections, so a moving sun bounces light correctly with no baked lightmaps. This project turns static lighting off entirely (r.AllowStaticLighting=False).

  • Virtual Shadow Maps: high-resolution shadows cached in pages; moving lights and wind-animated foliage invalidate the cache and cost frame time.

  • Temporal Super Resolution (TSR): renders below output resolution and reconstructs detail from previous frames (r.AntiAliasingMethod=4 here).

Lights use physical units, so exposure matters. A directional light's intensity is in lux and point or spot lights use lumens or candelas, with auto-exposure adapting like a camera. Real sunlight is on the order of 100,000 lux; this project uses a stylized 10 lux sun and scales its lamps to match (900 lm street lights, 90 lm porch lights).

Components declare mobility. Static, Stationary or Movable tells the engine what it may precompute and cache, so set it honestly: the level's tiles are Static, and the sun, moon and lamps are Movable.

Instancing makes thousands of objects cheap. One instanced static mesh component draws many copies of a mesh in a few draw calls. More than 2,200 trees placed from aerial imagery, plus shrubs, cars and poles, are ALHPropScatter actors holding hierarchical instanced components, and ALHGrassField streams instanced grass in cells around the camera.

Console variables control the renderer. Nearly every feature has an r.* variable, scalability groups (Low to Cinematic) set many at once, config files set project defaults, and ULHGameInstance::Init overrides a few at startup.

#10. Input, collision and movement

Enhanced Input separates what the player means from which key they press. An Input Action (UInputAction) is an intent with a value type: a bool (jump), a 1D axis (zoom) or a 2D axis (move). An Input Mapping Context (UInputMappingContext) maps keys and sticks to actions, with modifiers (dead zone, negate, swizzle axes) and triggers (pressed, held, released); contexts stack and swap at run time, such as a vehicle context over an on-foot one.

Actions and contexts are normally assets; this project builds them in code. ALHPlayerController::SetupInputComponent creates 15 actions with NewObject<UInputAction>, maps keys and sticks to them, adds a radial dead zone of 0.25 to the sticks because the test gamepad drifts, and binds each action to a handler:

Map(MoveAction, EKeys::W, /*swizzle*/ true);        // W feeds +Y of the 2D move axis
DeadZone(Map(MoveAction, EKeys::Gamepad_Left2D));
EIC->BindAction(MoveAction, ETriggerEvent::Triggered, this, &ALHPlayerController::OnMove);

Collision is a matrix of channels and responses. Every primitive component has an object type (WorldStatic, WorldDynamic, Pawn and others) and a response to each channel: Ignore, Overlap or Block. Named profiles bundle those settings; this project adds LHFoliage, so tree trunks block the cat but ignore the camera and visibility channels, and the camera boom passes through trees instead of snapping in.

Traces and sweeps are your ray casts and shape casts. LineTraceSingleByChannel casts a ray, SweepSingleByChannel moves a sphere, box or capsule along a segment, and overlap tests check a volume. APlayerCat::UpdateLedgeAssist sweeps a small sphere down in front of the cat near the top of a jump to find a ledge, then runs an overlap test to confirm the capsule fits before lifting the cat onto it.

Character movement is kinematic, not rigid-body physics. UCharacterMovementComponent integrates velocity from input acceleration, friction and gravity, then moves the capsule with collision sweeps and slides along whatever it hits, in substeps, with modes for walking, falling, swimming and flying. Rigid bodies such as crates, debris or vehicles are simulated by the Chaos physics engine instead, which integrates forces and solves contacts.

Tuning movement means setting its parameters. The cat's live in the ACatCharacter constructor: MaxWalkSpeed 360 cm/s (trot), JumpZVelocity 520 cm/s, GravityScale 1.45, AirControl 0.55, MaxStepHeight 26 cm and walkable slopes up to 52°. LaunchCharacter sets the velocity directly for the charged leap and the pounce.

Pawns ask to move; something else decides. AddMovementInput(Direction, Scale) queues a request that the movement component consumes on its next tick, whether a player or an AI made it. AI pawns plan on a navigation mesh: AAIController::MoveToLocation finds and follows a path, which is how the strays roam, and a pawn with no controller stays still unless bRunPhysicsWithNoController is set, which the man needed.

UnrealBuildTool (UBT) is the build system. It reads the C# rules, runs the header tool to generate reflection code, then drives MSVC and the linker; it also generates Visual Studio or Rider solutions. Think of CMake plus a code generator, with no CMakeLists to maintain. From a terminal:

"C:\Program Files\Epic Games\UE_5.8\Engine\Build\BatchFiles\Build.bat" LakeHighlandStrayEditor Win64 Development -Project="C:\Users\AlecF\Documents\Create Unreal Game\LakeHighlandStray\LakeHighlandStray.uproject" -WaitMutex

Live Coding patches a running editor. Press Ctrl+Alt+F11 in the editor to recompile changed .cpp files and patch them into the live process. It handles function bodies well; changes to headers, class layouts or reflection macros need the editor closed and a full build.

Config files are layered. Settings merge in order from engine defaults (Engine\Config\Base*.ini), the project's Config\Default*.ini, platform overrides, and per-user files in Saved\Config. A section such as [/Script/Engine.RendererSettings] sets defaults of that class, +Key= appends to an array and -Key= removes; the editor's Project Settings window edits these same files.

#12. Debugging and profiling

Visual Studio debugs Unreal like any C++ program. Generate a solution (right-click the .uproject > Generate Visual Studio project files), pick the Development Editor or DebugGame Editor configuration, and press F5: the editor launches under the debugger and your breakpoints hit during Play In Editor. The engine's Engine\Extras\VisualStudioDebugging\Unreal.natvis makes TArray, FString and FName readable in the watch window.

Logging goes to the Output Log and a file. UE_LOG(LogLH, Warning, TEXT("...")) writes to the editor's Output Log and to Saved\Logs\<Project>.log, filtered by category and verbosity (Verbose, Log, Display, Warning, Error, Fatal). GEngine->AddOnScreenDebugMessage prints on the screen instead. Shipping builds strip logging, which is why this project's automated test writes its own results.txt.

The console is a REPL for the running game. Press the tilde key (~) in a viewport or a Development build:

CommandWhat it does
stat fps, stat unitFrame rate; game-thread, render-thread, GPU and RHI times per frame
stat game, stat gpuBreakdowns of game-thread and GPU costs
ProfileGPUCaptures one frame's GPU passes with timings
show collisionDraws collision shapes
slomo 0.25Slows game time to a quarter
r.ScreenPercentage 50Sets any renderer variable live
t.MaxFPS 30Caps the frame rate

Unreal Insights is the profiler. Launch with -trace=default (or start a trace from the editor), then open the .utrace file in UnrealInsights.exe to see per-thread timelines, CPU scopes, GPU passes, memory and asset loading. Add your own scopes with TRACE_CPUPROFILER_EVENT_SCOPE(MyScope).

Debug drawing and inspection. DrawDebugLine, DrawDebugSphere and friends draw in the world for a frame or a set duration. During Play In Editor, F8 ejects the camera from the player so you can select and inspect any actor, and the apostrophe key opens the Gameplay Debugger for AI state.

Automate with command-line flags and tests. Custom flags like this project's -LHAutoTest are read with FParse::Param(FCommandLine::Get(), TEXT("LHAutoTest")). The engine also has an Automation framework for unit and functional tests; this project instead scripts a smoke test inside its GameMode that takes screenshots and logs measurements, run by Pipeline\ue\run_game.ps1.

#13. Unreal in aerospace work, and what to learn next

Aerospace and defense teams mostly use Unreal as the visual and sensor front end of a simulation whose models live elsewhere. A posting that asks for Unreal experience usually means: bring external simulation state into an Unreal scene, render it fast and correctly, and extend the engine in C++.

Where it shows upUnreal pieces involved
Out-the-window visuals for flight and mission simulatorsA georeferenced world, a camera driven by the simulation's state, multi-channel displays
Scenes on a real-world globeCesium for Unreal (free, open source; a full-scale WGS84 globe streamed as 3D Tiles), ArcGIS Maps SDK for Unreal Engine, the engine's GeoReferencing plugin
Autonomy and sensor testingSimulators built on Unreal such as CARLA (driving; version 0.10.0 moved to UE 5.5) and AirSim (drones and cars); USceneCaptureComponent2D renders synthetic camera feeds, traces stand in for range sensors
Domes, caves and video wallsnDisplay: one scene rendered across synchronized PCs and projectors
Remote and browser accessPixel Streaming: render on a server, stream video over WebRTC to a browser, send input back
Imagery and video productsMovie Render Queue for offline captures; editor Python for batch scene generation

What transfers from this project: converting a real-world frame into Unreal's (LHGeo::ToUE), loading external data at startup (ULHWorldData), driving actors from a computed model (ALHDayNight's solar position), headless automation through Python and command-line runs, and measuring performance (stat unit, ProfileGPU).

The classic first exercise for a simulation engineer is a UDP bridge. Write an actor that listens on a UDP port (FUdpSocketBuilder and FUdpSocketReceiver, in the Networking module), parses position and attitude, converts NED with the mapping from section 7, and sets a mesh's transform each frame, interpolating between packets. The receiver calls you on its own thread, so hand data to the game thread through a TQueue or a lock; the exercise touches modules, threads, time, coordinates and rendering at once.

A learning path, in order:

  1. Work through Part 2 and its exercises in this project.

  2. Learn the editor itself: viewport navigation, the Outliner, the Details panel, the Content Browser, Play In Editor. Epic's free learning portal hosts courses and tutorials.

  3. Build the UDP bridge, then put the aircraft on a Cesium globe.

  4. Make one Blueprint subclass of a C++ class and one UMG widget, so you can work with both halves of a typical team.

  5. Profile on your own hardware with stat unit and Unreal Insights.

  6. Read engine source for the classes you use; AActor and UCharacterMovementComponent are well commented, and the source is the final reference. Getting the source takes linked Epic and GitHub accounts.
